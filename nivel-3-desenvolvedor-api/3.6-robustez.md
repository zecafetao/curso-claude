# 3.6 Robustez

**Carga:** 3 h (1 h de leitura e experimentação, 2 h de exercício)

## Objetivo

Fazer um processamento longo terminar com um resultado confiável mesmo quando a API falha, a conexão cai, um pedido é recusado ou o script é interrompido no meio: nenhum registro perdido, nenhum pago duas vezes, e o gasto sob um teto.

## Por que importa no seu trabalho

Um script que funciona com 20 registros de teste ainda não está pronto para 20 mil. Em um processamento de duas horas, alguma coisa acontece: a API devolve um erro de sobrecarga, o Wi-Fi oscila, o notebook hiberna, um registro estranho gera um pedido inválido.

Sem preparo, cada um desses eventos tem um custo. O script para no registro 7.412, e você não sabe o que já foi feito. Recomeça do zero e paga de novo pelos 7.411. Ou pior: o script segue, pula registros em silêncio, e a base importada tem menos contatos do que a base recebida, sem que ninguém perceba.

Robustez, aqui, é uma lista de garantias verificáveis. Este módulo constrói cada uma.

## Conteúdo

### 1. O que pode dar errado

| Evento | Como aparece | O que fazer |
| --- | --- | --- |
| Pedido inválido | Erro 400 | Corrigir o pedido. Repetir igual não resolve |
| Chave inválida ou sem permissão | Erro 401 ou 403 | Parar tudo |
| Problema de cobrança | Erro 402 | Parar tudo e resolver no Console |
| Recurso inexistente, como um nome de modelo errado | Erro 404 | Parar e corrigir a configuração |
| Requisição grande demais | Erro 413 | Reduzir a entrada |
| Limite de ritmo ou limite de gasto atingido | Erro 429 | Esperar e tentar de novo. Se for o limite de gasto, parar |
| Falha ou sobrecarga do servidor | Erro 500, 504 ou 529 | Esperar e tentar de novo |
| Conexão caiu ou tempo esgotado | Erro de conexão, sem código | Esperar e tentar de novo |
| Resposta cortada | `stop_reason` igual a `max_tokens` | Não usar a resposta. Aumentar o limite |
| Pedido recusado | `stop_reason` igual a `refusal` | Registrar e seguir |
| Script interrompido | Ctrl+C, queda de energia, hibernação | Retomar de onde parou |
| Erro de programação em laço | Chamadas repetidas sem fim | Teto de custo e limite de gasto |

A tabela separa três grupos. Os erros **temporários** passam sozinhos, e a resposta é esperar e repetir. Os erros **do pedido** não passam, e repetir só gasta tempo. Os dois últimos eventos de `stop_reason` não são erros para a API: a chamada deu certo, com código 200, e é o seu script que precisa conferir.

### 2. Os erros da API

A API informa cada erro com um código de status, como no módulo P.4, e um tipo.

| Código | Tipo | Significado |
| --- | --- | --- |
| 400 | `invalid_request_error` | O formato ou o conteúdo da requisição está errado |
| 401 | `authentication_error` | Problema com a chave |
| 402 | `billing_error` | Problema de cobrança ou pagamento |
| 403 | `permission_error` | A chave não tem permissão para o recurso |
| 404 | `not_found_error` | O recurso não existe |
| 413 | `request_too_large` | A requisição passa do tamanho máximo |
| 429 | `rate_limit_error` | Limite de ritmo ou de gasto atingido |
| 500 | `api_error` | Erro interno da Anthropic |
| 504 | `timeout_error` | A requisição esgotou o tempo de processamento |
| 529 | `overloaded_error` | A API está sobrecarregada no momento |

(Documentação oficial, novembro de 2026.)

Os trechos das seções 2 a 6 continuam um ao outro. Escreva-os em um arquivo `testar_robustez.py`, com o `retomada.py` do gabarito e o seu `extrair_contatos.py` na pasta. No exercício, você escreve a sua versão da retomada.

No SDK, cada código vira uma **exceção**, o nome técnico dos erros que você trata com `try` e `except`. Há uma classe para cada caso, e as classes formam uma hierarquia: `RateLimitError` é um tipo de `APIStatusError`, que é um tipo de `APIError`. Por isso a ordem dos `except` importa. O Python usa o primeiro que servir, então o mais específico vem antes.

```python
import anthropic

import claude_util as cu

cliente = cu.criar_cliente()

try:
    resposta = cu.chamar(cliente, [{"role": "user", "content": "O que é opt-in?"}], esforco="low")
    print(resposta.stop_reason)
except anthropic.AuthenticationError:
    print("Chave inválida ou ausente. Confira a variável ANTHROPIC_API_KEY.")
except anthropic.BadRequestError as erro:
    print(f"Pedido inválido: {erro.message}")
except anthropic.RateLimitError:
    print("Limite atingido. Tente mais tarde.")
except anthropic.APIStatusError as erro:               # qualquer outro código de erro
    print(f"Erro {erro.status_code}: {erro.message}")
except anthropic.APIConnectionError:                    # não houve resposta
    print("Falha de conexão.")
```

A mensagem de um erro 400 diz o que a API recusou, quase sempre com o nome do parâmetro. Leia a mensagem inteira antes de mudar o código. Quando precisar de suporte, informe o `erro.request_id`, que identifica a requisição do lado da Anthropic.

### 3. O que o SDK já faz

O SDK repete sozinho as requisições que falham por erro de conexão, por erro 429 e por erros 500 em diante. São duas novas tentativas por padrão, com espera crescente entre elas, respeitando o tempo indicado pela API quando ela informa. O tempo máximo de espera por uma resposta é de 10 minutos.

Os dois valores podem ser mudados ao criar o cliente:

```python
cliente_paciente = anthropic.Anthropic(max_retries=4, timeout=120.0)
print(cliente_paciente.max_retries)
```

Na prática, muitas falhas curtas nem chegam ao seu código. O que chega é o que resistiu a três tentativas. Para um processamento longo, isso ainda é pouco: uma sobrecarga de dois minutos derruba o script. A camada seguinte, que você constrói neste módulo, espera mais e não perde o que já foi feito.

### 4. Limites de ritmo

A API limita o uso por minuto, por modelo, em três medidas: requisições, tokens de entrada e tokens de saída. Os limites dependem da faixa de uso da conta, que sobe conforme o histórico de consumo. Contas novas começam nas faixas mais baixas. Os valores atuais estão na página de limites do Console.

O que você precisa saber para um processamento em laço:

- O limite se recompõe de forma contínua. Não há uma "virada do minuto" a esperar.
- A resposta 429 pode trazer um cabeçalho `retry-after`, com os segundos de espera. O SDK lê e respeita.
- Tokens lidos do cache não contam no limite de tokens de entrada. O cache do módulo 3.5 também aumenta o volume que cabe por minuto.
- Um laço que faz uma chamada de cada vez raramente bate no limite. Quem bate é o processamento em paralelo, que o curso não usa. Para volume alto sem pressa, use lote.
- O erro 429 também aparece quando o limite de gasto mensal é atingido. Nesse caso, esperar não adianta, e o script precisa parar.

### 5. Respostas que não são erro: corte e recusa

A API devolve código 200, sem exceção, em dois casos que o script não pode tratar como sucesso.

**Corte por `max_tokens`.** Já visto nos módulos 3.1 e 3.3. A resposta está incompleta e não deve ser usada.

**Recusa.** Os modelos atuais têm filtros de segurança, voltados a temas como segurança cibernética e biologia. Um pedido legítimo pode ser recusado por engano, por exemplo um texto de contato que fale de um laboratório ou de um sistema de segurança. A resposta vem com `stop_reason` igual a `refusal`, e o conteúdo pode vir vazio.

```python
if resposta.stop_reason == "refusal":
    detalhes = resposta.stop_details
    categoria = detalhes.category if detalhes else "não informada"
    print(f"Pedido recusado. Categoria: {categoria}")
elif resposta.stop_reason == "max_tokens":
    print("Resposta cortada. Não use o conteúdo.")
else:
    print(cu.texto_da_resposta(resposta))
```

Três regras para recusas:

- **Ligue o plano B.** Com `fallbacks="default"`, a API refaz o pedido recusado em outro modelo, dentro da mesma chamada. A função `chamar` já faz isso. Se o `stop_reason` final ainda for `refusal`, todos os modelos tentados recusaram.
- **Não repita o mesmo pedido.** Uma recusa não é um erro temporário. O mesmo texto será recusado de novo.
- **Registre e siga.** O registro recusado entra no resultado com a situação `recusado`, para tratamento manual. A fila continua.

Dois limites do plano B: ele não existe no processamento em lote nem no Haiku 5.5. Nesses casos, a recusa chega direto ao seu script. E uma observação de custo: quando o plano B entra em ação, a resposta é cobrada pelo preço do modelo que respondeu. O cálculo do `claude_util.py` usa o preço do modelo pedido e fica aproximado nesses casos. A referência é a fatura do Console.

### 6. Retomada

A garantia central de um processamento longo: **se parar, continua de onde parou**. O mecanismo é um arquivo de progresso.

1. Cada item concluído vira uma linha no arquivo, gravada antes de o script passar ao item seguinte.
2. Ao começar, o script lê o arquivo e pula os itens já concluídos.
3. O arquivo final de saída é montado a partir do progresso, com uma linha por item de entrada.

O formato do arquivo de progresso é o **JSONL**: um JSON por linha. A vantagem sobre um JSON único é que acrescentar uma linha não exige reescrever o arquivo, e uma interrupção no meio da gravação estraga, no máximo, a última linha.

```
{"id": "C01", "situacao": "ok", "resultado": {"nome": "Xênia", ...}, "custo": 0.0021}
{"id": "C02", "situacao": "ok", "resultado": {"nome": "Karina", ...}, "custo": 0.0019}
{"id": "C10", "situacao": "recusado", "custo": 0.0004}
```

Cada item termina em uma de quatro situações:

| Situação | Significado | Na próxima execução |
| --- | --- | --- |
| `ok` | Há resultado | É pulado |
| `recusado` | O pedido foi recusado | É pulado. Vai para tratamento manual |
| `erro` | Falhou, por erro temporário que persistiu ou por erro do pedido | É tentado de novo |
| `pendente` | Ainda não foi processado | É processado |

A soma das quatro é sempre o total de itens de entrada. Essa igualdade é a garantia de que nenhum registro se perdeu, e o script a mostra no resumo.

O módulo [`gabarito/retomada.py`](gabarito/retomada.py) implementa o mecanismo de forma genérica. Ele não chama a API: recebe a lista de itens e a função que processa um item.

```python
from pathlib import Path

import retomada

Path("progresso_teste.jsonl").unlink(missing_ok=True)       # começa do zero


def processar(texto):
    """Processamento de mentira: devolve o texto em maiúsculas e cobra 1 centavo."""
    if texto == "":
        raise ValueError("texto vazio")
    return {"situacao": "ok", "resultado": {"texto": texto.upper()}, "custo": 0.01}


itens = [("A", "primeiro"), ("B", ""), ("C", "terceiro")]

resumo = retomada.processar_com_retomada(itens, processar, "progresso_teste.jsonl")
print(retomada.texto_do_resumo(resumo))

resumo = retomada.processar_com_retomada(itens, processar, "progresso_teste.jsonl")
print(retomada.texto_do_resumo(resumo))
```

Na segunda execução, os itens A e C são pulados, e só o B é tentado de novo. O custo acumulado não dobra.

A função que processa um item devolve um dicionário com a `situacao` e, quando houver, o `resultado`, o `custo` e um `detalhe`. Para a extração do módulo 3.3, ela fica assim:

```python
from extrair_contatos import extrair


def processar_com(cliente):
    """Devolve a função que processa um texto, no formato que a retomada espera."""
    def processar(texto):
        contato, resposta = extrair(cliente, texto)
        custo = cu.custo_em_dolares(resposta.usage)
        if resposta.stop_reason == "refusal":
            return {"situacao": "recusado", "custo": custo}
        if contato is None:
            return {"situacao": "erro", "custo": custo, "detalhe": f"resposta incompleta ({resposta.stop_reason})"}
        return {"situacao": "ok", "resultado": contato, "custo": custo}
    return processar


processar_texto = processar_com(cliente)
print(processar_texto("Ana Almeida, compradora da Alimentos Alfa, ana.almeida@alfa.example"))
```

Uma função definida dentro de outra, como `processar` dentro de `processar_com`, enxerga as variáveis da função de fora. É a forma de entregar à retomada uma função que recebe só o texto, mas usa o cliente.

### 7. Repetição com espera e freios

Dentro da retomada, cada item passa por uma segunda camada de tentativas, acima das do SDK:

| Tipo de erro | Tratamento |
| --- | --- |
| Temporário (429, 500 em diante, conexão) | Até quatro tentativas, com espera de 2, 4 e 8 segundos. Se a API indicar um tempo maior, vale o maior |
| Chave ou permissão (401, 403) | A execução para na hora. O progresso já gravado é mantido |
| Qualquer outro | O item é registrado como `erro`, com a mensagem, e a fila segue |

A espera que dobra a cada tentativa tem um motivo: se a API está sobrecarregada, insistir em intervalos curtos piora a sobrecarga e não resolve o seu problema.

Três **freios** impedem que uma execução saia do controle:

- **Teto de custo.** O custo de cada item é somado, contando as execuções anteriores. Ao atingir o teto, a execução para, com os itens restantes como pendentes.
- **Falhas seguidas.** Três itens seguidos com erro indicam um problema geral, e não dos itens: a API fora do ar, o limite de gasto atingido, um nome de modelo errado. A execução para, em vez de marcar a base inteira como erro.
- **Limite de gasto no Console.** É a última barreira e vale mesmo que o seu código tenha um defeito.

Uma interrupção com Ctrl+C é tratada como parada normal: o script mostra o resumo e termina. Basta rodar de novo.

### 8. Testar as falhas sem gastar

Falhas reais são raras e não aparecem quando você quer testar. A solução é simular: trocar a função que chama a API por uma que falha de propósito.

O [`gabarito/falhas_simuladas.py`](gabarito/falhas_simuladas.py) faz isso com 12 itens de mentira. O item 3 sofre dois erros temporários antes de funcionar, o item 5 tem um pedido inválido, o item 7 é recusado e, no item 9, o script simula um Ctrl+C. Ele roda três execuções seguidas sobre o mesmo arquivo de progresso, sem chamar a API.

O mesmo princípio vale para os testes automatizados. O [`gabarito/test_nivel3.py`](gabarito/test_nivel3.py) testa a retomada, o teto de custo e as falhas seguidas com funções de mentira, em um segundo e sem créditos.

### 9. Lista de conferência de um processamento

Antes de rodar um processamento longo com dados reais, confira:

1. O `stop_reason` é conferido antes de usar qualquer resposta.
2. Há um arquivo de progresso, gravado a cada item.
3. Rodar duas vezes seguidas não refaz nem cobra de novo o que terminou.
4. O arquivo de saída tem uma linha por item de entrada, com a situação de cada um.
5. O resumo mostra ok, recusado, erro e pendente, e a soma é o total de itens.
6. Erros temporários são repetidos com espera crescente.
7. Há teto de custo no script e limite de gasto no Console.
8. As falhas foram testadas com simulação.
9. O script foi rodado primeiro em uma amostra pequena.

## Exemplo aplicado

**Situação.** A extração de contatos do módulo 3.3 vai rodar sobre 8 mil mensagens acumuladas de três feiras. Pela medição que você fez, isso leva algumas horas. O script do 3.3 grava o CSV de saída só no fim do laço e não trata erros.

**O que acontece sem preparo.** Na mensagem 3.200, a API devolve erro 529 três vezes seguidas, e o script termina com uma exceção. O CSV de saída ficou pela metade ou vazio, conforme o momento da falha. Você pagou por 3.199 extrações que precisará refazer.

**O que muda com a retomada.**

| Evento | Comportamento |
| --- | --- |
| Erro 529 na mensagem 3.200 | Novas tentativas com espera de 2, 4 e 8 segundos. Se persistir, a mensagem fica como `erro` e a fila segue |
| Três mensagens seguidas com erro | A execução para com o aviso de falhas seguidas. As 3.199 primeiras estão gravadas |
| Você roda de novo uma hora depois | As 3.199 são puladas. As três com erro são tentadas de novo, e a fila continua |
| Uma mensagem é recusada | Fica como `recusado`, com o custo registrado, e vai para uma lista de tratamento manual |
| O gasto chega ao teto | A execução para. Você decide se aumenta o teto |
| Fim | O CSV tem 8 mil linhas, cada uma com a situação. O resumo fecha com o total |

**A informação para quem recebe a base.** "8.000 mensagens: 7.914 extraídas, 9 recusadas para tratamento manual, 77 sem dados de contato. Custo: US$ X." Um número que fecha com o total recebido é o que permite ao cliente confiar que nada sumiu no caminho.

A solução completa está em [`gabarito/extrair_com_retomada.py`](gabarito/extrair_com_retomada.py).

## Erros comuns

- Gravar o resultado só no fim do laço.
- Tratar toda exceção do mesmo jeito, com um `except Exception` que repete tudo ou ignora tudo.
- Repetir sem espera, em laço apertado, um erro de sobrecarga.
- Repetir um pedido recusado ou um pedido inválido.
- Pular registros com erro sem registrá-los, e entregar uma saída menor que a entrada.
- Recomeçar do zero depois de uma interrupção, pagando de novo.
- Não ter teto de custo no script por confiar só no limite do Console.
- Considerar o script pronto sem nunca ter testado uma falha.
- Tratar `stop_reason` igual a `max_tokens` ou `refusal` como sucesso porque não houve exceção.
