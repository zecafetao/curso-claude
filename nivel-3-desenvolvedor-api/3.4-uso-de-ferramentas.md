# 3.4 Uso de ferramentas

**Carga:** 5 h (1 h 30 de leitura e experimentação, 3 h 30 de exercício)

## Objetivo

Dar ao Claude funções suas, que ele pede para executar durante a resposta, e desenhar essas funções de modo que os números sejam exatos, os dados pessoais não saiam do computador e nenhuma ação aconteça sem o seu controle.

## Por que importa no seu trabalho

Até aqui, o Claude só conhecia o que você colocava na mensagem. Para responder "quantos contatos de Compras em SP têm consentimento?", você teria de enviar a base inteira, pagar por ela e ainda confiar em uma contagem feita por um modelo de linguagem, que erra contas em tabelas longas (módulo 2.6).

Com ferramentas, a pergunta chega em linguagem natural, o Claude decide qual função sua chamar e com que filtros, o seu código conta na base e devolve o número. A interpretação fica com o modelo e a conta fica com o código. É a mesma divisão do módulo 3.3, agora no sentido inverso: o modelo pede dados ao seu código.

Este módulo é a base do Nível 4. Um agente é um modelo com ferramentas em um laço.

## Conteúdo

### 1. O que é uma ferramenta

Uma **ferramenta** é uma função sua que você descreve para o modelo. O modelo não executa nada. O que ele faz é responder com um pedido: "chame a função `contar_contatos` com `area=Compras` e `uf=SP`". O seu código executa a função e devolve o resultado em uma nova mensagem. Com o resultado em mãos, o modelo escreve a resposta, ou pede outra ferramenta.

```
Você:    "Quantos contatos de Compras em SP têm consentimento?"
Claude:  pedido de ferramenta -> contar_contatos(area="Compras", uf="SP", consentimento="S")
Código:  executa a função na base -> {"quantidade": 2}
Claude:  "São 2 contatos."
```

Esse vaivém é o **laço de ferramentas**. Cada volta é uma chamada à API.

Uma ferramenta tem três partes:

| Parte | O que é | Para que serve |
| --- | --- | --- |
| Nome | Um identificador, como `contar_contatos` | O modelo usa o nome no pedido |
| Descrição | Um texto que diz o que a função faz e quando usar | É o que o modelo lê para decidir. Vale como um prompt |
| Esquema de entrada | Um JSON Schema dos parâmetros | Define o que o modelo pode pedir |

As funções deste módulo estão em [`gabarito/ferramentas.py`](gabarito/ferramentas.py). Elas são Python comum, sem nenhuma chamada à API, e podem ser testadas sozinhas:

```python
import json

import claude_util as cu
import ferramentas

print(ferramentas.resumir_base("area"))
print(ferramentas.contar_contatos(area="Compras", uf="SP", consentimento="S"))
```

Os trechos das seções 1 a 5 continuam um ao outro. Escreva-os em um arquivo `testar_ferramentas.py`, com o `ferramentas.py` do gabarito na pasta. No exercício, você escreve o seu.

### 2. O laço, passo a passo

Para entender o mecanismo, faça uma volta à mão. Primeiro, a definição da ferramenta, como a API recebe:

```python
DEFINICOES = [
    {
        "name": "resumir_base",
        "description": (
            "Conta os contatos da base tratada por valor de uma coluna. Use quando a pergunta pedir "
            "a distribuição dos contatos, como 'quantos por área'."
        ),
        "strict": True,
        "input_schema": {
            "type": "object",
            "properties": {
                "coluna": {
                    "type": "string",
                    "enum": ferramentas.COLUNAS_PERMITIDAS,
                    "description": "A coluna a resumir.",
                }
            },
            "required": ["coluna"],
            "additionalProperties": False,
        },
    }
]
```

O esquema é o mesmo JSON Schema do módulo 3.3. `strict: True` aplica à entrada da ferramenta a garantia de formato das saídas estruturadas: o pedido do modelo sempre obedece ao esquema.

A primeira chamada leva a pergunta e as ferramentas disponíveis:

```python
cliente = cu.criar_cliente()
mensagens = [{"role": "user", "content": "Quantos contatos há por área?"}]

resposta = cu.chamar(cliente, mensagens, tools=DEFINICOES)

print(resposta.stop_reason)
for bloco in resposta.content:
    if bloco.type == "tool_use":
        print(bloco.id, bloco.name, bloco.input)
```

O motivo de parada é `tool_use`, e o conteúdo traz um bloco de pedido com três campos: um identificador (`id`), o nome da ferramenta e a entrada, já como dicionário.

Agora o seu código executa e devolve:

```python
# 1. A resposta do modelo entra no histórico, inteira.
mensagens.append({"role": "assistant", "content": resposta.content})

# 2. Cada pedido é executado. Os resultados voltam todos em uma única mensagem.
resultados = []
for bloco in resposta.content:
    if bloco.type == "tool_use":
        resultado = ferramentas.resumir_base(**bloco.input)
        resultados.append({
            "type": "tool_result",
            "tool_use_id": bloco.id,
            "content": json.dumps(resultado, ensure_ascii=False),
        })
mensagens.append({"role": "user", "content": resultados})

# 3. Nova chamada, com o histórico completo.
resposta = cu.chamar(cliente, mensagens, tools=DEFINICOES)
print(resposta.stop_reason)
print(cu.texto_da_resposta(resposta))
```

Os pontos que mais causam erro:

- O `tool_use_id` do resultado precisa ser o `id` do pedido. É assim que o modelo liga um ao outro.
- O resultado vai em uma mensagem de papel `user`. Não existe um papel próprio para ferramentas.
- O modelo pode pedir mais de uma ferramenta na mesma resposta. Todos os resultados voltam juntos, na mesma mensagem.
- `**bloco.input` passa o dicionário como parâmetros da função: `{"coluna": "area"}` vira `coluna="area"`.

O laço completo repete isso até o motivo de parada deixar de ser `tool_use`, com um limite de voltas. A versão de referência está em [`gabarito/laco_manual.py`](gabarito/laco_manual.py). Ela também trata a falha de uma ferramenta: o erro volta como resultado, com `"is_error": True`, e o modelo decide se corrige o pedido ou explica o problema.

### 3. O executor do SDK

Escrever o laço à mão ensina o mecanismo. No dia a dia, o SDK tem um **executor de ferramentas** que faz o laço por você. Ele precisa de duas coisas: as funções marcadas como ferramentas e os parâmetros da chamada.

```python
from anthropic import beta_tool


@beta_tool
def contar_contatos(area: str = "", uf: str = "", consentimento: str = "", origem: str = "") -> str:
    """Conta os contatos da base tratada que cumprem todos os filtros informados.

    Use quando a pergunta combinar condições, como "contatos de Compras em SP com consentimento".

    Args:
        area: Compras, Produção, Marketing, Comercial, Diretoria ou Outros. Vazio para todas.
        uf: Sigla do estado, como SP. Vazio para todos.
        consentimento: S ou N. Vazio para os dois.
        origem: Credenciamento, Expositor, Site, Evento ou Compra de base. Vazio para todas.
    """
    return json.dumps(ferramentas.contar_contatos(area, uf, consentimento, origem), ensure_ascii=False)


print(json.dumps(contar_contatos.to_dict(), ensure_ascii=False, indent=2)[:700])
```

Três elementos novos de Python:

- **Decorador.** A linha `@beta_tool` antes da função entrega a função ao SDK, que devolve uma ferramenta pronta.
- **Anotações de tipo.** `area: str = ""` diz que o parâmetro é um texto com valor padrão vazio, e `-> str` diz que a função devolve texto. O SDK usa as anotações para montar o esquema de entrada.
- **Docstring com `Args:`.** A primeira linha e o parágrafo seguinte viram a descrição da ferramenta. Cada linha de `Args:` vira a descrição de um parâmetro.

O `print` mostra a definição gerada. Confira nela o que o modelo vai ler.

Com a ferramenta pronta, o executor faz o laço:

```python
executor = cliente.beta.messages.tool_runner(
    model=cu.MODELO,
    max_tokens=16000,
    tools=[contar_contatos],
    messages=[{"role": "user", "content": "Quantos contatos de Compras em SP têm consentimento?"}],
    betas=[cu.BETA_FALLBACK],
    fallbacks="default",
    max_iterations=8,
    thread=False,
)

total = cu.novo_total()
for mensagem in executor:                      # cada volta do laço entrega uma resposta do modelo
    cu.somar_uso(total, mensagem.usage)
    for bloco in mensagem.content:
        if bloco.type == "tool_use":
            print("pediu:", bloco.name, bloco.input)

print(cu.texto_da_resposta(mensagem))          # a última mensagem é a resposta final
print(cu.resumo_do_total(total))
```

| Parâmetro | O que faz |
| --- | --- |
| `tools` | A lista de ferramentas |
| `max_iterations` | O máximo de voltas. Sem ele, um laço que não converge continua gastando |
| `thread=False` | Faz cada requisição levar a conversa inteira, como no laço manual |
| `betas` e `fallbacks` | O plano B para recusas, já usado pela função `chamar` |

Sobre o `thread=False`: nas versões recentes do SDK, o executor pode guardar a conversa no servidor por alguns minutos, para não reenviar tudo a cada volta. O recurso está em beta (novembro de 2026) e não muda o preço. O curso desliga para que o comportamento seja igual ao do laço manual e para que nada fique guardado fora do seu computador entre as voltas.

Se uma ferramenta gerar um erro do Python, o executor captura e devolve o erro ao modelo como resultado. O laço não quebra.

### 4. Como desenhar boas ferramentas

O desenho das ferramentas decide a qualidade, o custo e a segurança do assistente. Seis regras.

**1. Uma ferramenta por pergunta de negócio.** `contar_contatos` e `validar_arquivo` são perguntas que alguém faz. Uma ferramenta genérica, como "executar uma consulta qualquer" ou "ler um arquivo qualquer", entrega ao modelo um poder que você não consegue prever nem testar.

**2. A descrição diz quando usar.** "Conta os contatos" descreve a função. "Use quando a pergunta combinar condições" orienta a escolha entre ferramentas parecidas. Escreva a descrição para alguém que nunca viu a base.

**3. Parâmetros fechados quando possível.** Uma lista de valores aceitos (`enum`) ou uma descrição com as opções reduz pedidos inválidos.

**4. Ferramentas devolvem resumos, não linhas.** Tudo o que uma ferramenta devolve é enviado à API e entra na conversa. Se `contar_contatos` devolvesse as linhas encontradas, nomes e e-mails sairiam do computador a cada pergunta, e você pagaria tokens por eles. As ferramentas do módulo devolvem contagens. `resumir_base` aceita só colunas de categoria e recusa a coluna `email`.

**5. Um erro claro é melhor que um zero.** Se o modelo pedir `area="Vendas"`, que não existe na base, a contagem daria zero, e zero parece uma resposta. A função confere os valores e devolve `{"erro": "Valor inválido para area..."}`. Com a mensagem, o modelo corrige o pedido.

**6. O pedido do modelo é uma entrada não confiável.** O modelo pode errar, e um texto malicioso dentro de um documento ou de uma página da web pode induzi-lo a pedir o que não deve (a injeção de instruções do módulo 2.5). A função se protege como se protegeria de qualquer entrada externa. `validar_arquivo` aceita só o nome de um arquivo `.csv` da pasta de dados. Um pedido com caminho, como `../outra_pasta/base.csv`, é recusado pela função, qualquer que seja a instrução dada ao modelo.

A regra 6 separa dois tipos de proteção. Uma instrução de sistema ("não leia arquivos fora da pasta") é um pedido, que o modelo costuma seguir. Uma conferência no código é uma garantia. Para o que não pode acontecer, use a garantia.

### 5. Ferramentas que rodam na Anthropic

As ferramentas das seções anteriores rodam no seu computador. Há também **ferramentas de servidor**, que a Anthropic executa. A mais útil para o seu trabalho é a busca na web:

```python
BUSCA_NA_WEB = {"type": "web_search_20260209", "name": "web_search", "max_uses": 3}
```

Basta incluir esse dicionário na lista `tools`. O modelo decide quando buscar, a busca acontece do lado da Anthropic, e a resposta chega com os resultados já usados, com as fontes. O seu código não executa nada.

| | Ferramenta sua | Ferramenta de servidor |
| --- | --- | --- |
| Onde roda | No seu computador | Na Anthropic |
| Quem executa | O seu código, no laço | A API, dentro da mesma chamada |
| Acesso | Aos seus arquivos e sistemas | À internet pública |
| Custo extra | Nenhum, além dos tokens | A busca na web custa 10 dólares por mil buscas, mais os tokens do conteúdo trazido |

O preço da busca é o de novembro de 2026. `max_uses` limita o número de buscas por pergunta. Sem limite, uma pergunta aberta pode gerar muitas buscas, e cada uma traz milhares de tokens de resultados para a conversa.

Em respostas com busca, o conteúdo traz blocos de tipo `server_tool_use` (o pedido) e blocos com os resultados. Uma busca demorada pode terminar com o motivo de parada `pause_turn`: a resposta foi pausada e precisa ser retomada. O executor do SDK retoma sozinho.

Os cuidados do módulo 2.5 continuam valendo: o que vem da web é texto de terceiros. Confira a fonte de cada número antes de usar, e lembre que uma página pode conter instruções escritas para enganar modelos.

### 6. Ações com efeito e aprovação

As três ferramentas deste módulo só leem. Nenhuma altera arquivo, envia e-mail ou grava no CRM. Isso é uma decisão de desenho, e ela muda o risco:

| Tipo de ferramenta | Exemplo | Pior caso de um pedido errado |
| --- | --- | --- |
| Só leitura, com resumo | Contar contatos, validar um arquivo | Uma resposta errada, que você confere |
| Leitura com dados pessoais | Listar contatos de um segmento | Dados pessoais enviados à API |
| Com efeito reversível | Gravar um arquivo novo em uma pasta de saída | Um arquivo a mais |
| Com efeito irreversível | Enviar um disparo, apagar registros, importar no CRM | Dano real |

Para ferramentas com efeito, a regra é: o modelo propõe e uma pessoa aprova. A forma mais simples é a função pedir confirmação antes de agir:

```python
def confirmar(nome, entrada):
    """Mostra o que o assistente quer executar e pede a confirmação de uma pessoa."""
    resposta = input(f"O assistente quer executar {nome} com {entrada}. Confirmar? (s/n) ")
    return resposta.strip().lower() == "s"
```

Uma ferramenta que grava ou envia chamaria `confirmar` antes de agir e devolveria "ação não autorizada" em caso de negativa. O Nível 4 desenvolve esse assunto: permissões, aprovação e limites de um agente.

Comece sempre pelo menor poder que resolve o problema. Um assistente que só lê e resume já elimina boa parte do trabalho manual, com risco baixo.

### 7. O custo do laço

Cada volta é uma chamada, e cada chamada reenvia tudo: as instruções, as definições das ferramentas, a pergunta, os pedidos e os resultados anteriores.

- As definições das ferramentas são cobradas como entrada em todas as voltas. Dez ferramentas com descrições longas pesam em cada chamada.
- Um resultado grande, como um resumo com 500 valores distintos, é cobrado na volta em que chega e em todas as seguintes. `resumir_base` devolve só os 20 valores mais frequentes.
- Uma pergunta que exige três consultas custa pelo menos quatro chamadas.

O resumo de uso que o assistente mostra ao fim de cada pergunta é a forma de acompanhar. O módulo 3.5 trata das técnicas de redução.

Nos modelos atuais, não é possível obrigar o uso de uma ferramenta específica. A escolha é do modelo, orientada pelas descrições e pelas instruções de sistema.

## Exemplo aplicado

**Situação.** A equipe de atendimento pergunta ao time de dados, várias vezes por dia: quantos contatos temos de tal área, em tal estado, com consentimento? E, antes de cada importação: este arquivo está pronto? Você quer um assistente que responda com números exatos da base tratada.

**As ferramentas.** Três, todas de leitura, todas com resumo:

| Ferramenta | Pergunta que responde | Proteção |
| --- | --- | --- |
| `resumir_base(coluna)` | Como os contatos se distribuem por área, UF, origem? | Só colunas de categoria. `email`, `nome` e `telefone` são recusadas |
| `contar_contatos(area, uf, consentimento, origem)` | Quantos contatos cumprem estas condições? | Valores fora da lista geram erro, e não zero |
| `validar_arquivo(nome_arquivo)` | Este arquivo está no layout? | Só arquivos `.csv` da pasta de dados, pelo nome |

**As instruções de sistema.**

```python
SISTEMA = (
    "Você apoia uma equipe de CRM. Para qualquer número sobre a base de contatos ou sobre um arquivo "
    "de importação, use as ferramentas: não estime. Use a busca na web só para informações externas, "
    "como dados de mercado. Você não altera nem apaga arquivos; se pedirem isso, explique que não tem "
    "essa ferramenta. Respostas curtas, com os números que as ferramentas devolveram."
)
print(len(SISTEMA))
```

**Uma pergunta e o que acontece.** "Que percentual dos contatos com consentimento é de SP?"

1. O modelo pede `contar_contatos(consentimento="S")`. O código devolve 57.
2. O modelo pede `contar_contatos(uf="SP", consentimento="S")`. O código devolve 8. Os dois pedidos podem vir na mesma volta.
3. O modelo responde: 8 de 57, cerca de 14%.

As contagens são exatas, porque vieram do código. A divisão foi feita pelo modelo, e é a parte que você confere: 8 ÷ 57 = 14,0%. Se o percentual fosse entrar em um relatório, a divisão também deveria ser de uma ferramenta.

**Um pedido que deve ser recusado.** "Liste os e-mails dos contatos de Diretoria." Não existe ferramenta que devolva dados individuais, e `resumir_base` recusa a coluna `email`. O assistente explica que só consegue informar quantidades. A recusa não depende da boa vontade do modelo: o dado não tem por onde sair.

A solução completa está em [`gabarito/assistente.py`](gabarito/assistente.py).

## Erros comuns

- Achar que o modelo executa a ferramenta. Quem executa é o seu código.
- Devolver o resultado com um `tool_use_id` diferente do `id` do pedido.
- Enviar os resultados de pedidos simultâneos em mensagens separadas.
- Não pôr limite de voltas no laço.
- Escrever descrições que dizem o que a função faz, mas não quando usar.
- Fazer a ferramenta devolver linhas da base, com dados pessoais, em vez de um resumo.
- Devolver zero ou lista vazia para um filtro inválido, em vez de um erro.
- Proteger um limite só com instrução de sistema, sem conferência no código.
- Começar por ferramentas que alteram ou enviam, antes de dominar as que só leem.
- Usar um número vindo da busca na web sem abrir a fonte.

## Checagem rápida

1. Quem executa uma ferramenta: o modelo ou o seu código? O que o modelo faz?
2. Por que as ferramentas do módulo devolvem contagens, e não as linhas encontradas?
3. Qual é a diferença entre proteger um limite com uma instrução de sistema e com uma conferência no código?
4. Por que `contar_contatos(area="Vendas")` devolve um erro, e não zero?
5. Uma pergunta fez o modelo pedir três ferramentas, uma por volta. Quantas chamadas à API ela custou, no mínimo?

<details>
<summary>Respostas</summary>

1. O seu código. O modelo só responde com um pedido, que traz o nome da ferramenta e a entrada. O código executa a função e devolve o resultado em uma nova mensagem.
2. Porque tudo o que a ferramenta devolve é enviado à API e entra na conversa. Linhas da base levariam dados pessoais para fora do computador e custariam tokens. A contagem responde à pergunta sem isso.
3. A instrução é um pedido, que o modelo costuma seguir, mas pode não seguir por erro ou por indução de um texto malicioso. A conferência no código vale sempre, qualquer que seja o pedido.
4. Porque zero pareceria uma resposta correta, e o assistente informaria que não há contatos. O erro mostra ao modelo que o valor não existe e quais são os valores aceitos.
5. Quatro: três chamadas que terminaram em pedido de ferramenta e uma com a resposta final.
