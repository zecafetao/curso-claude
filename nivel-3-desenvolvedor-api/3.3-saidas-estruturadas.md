# 3.3 Saídas estruturadas

**Carga:** 3 h (1 h de leitura e experimentação, 2 h de exercício)

## Objetivo

Receber do Claude dados em um formato fixo, que o seu código lê sem tratamento manual, e medir a taxa de acerto de uma extração contra um gabarito.

## Por que importa no seu trabalho

Parte das suas bases não chega em colunas. Chega em assinaturas de e-mail, mensagens de WhatsApp, campos de observação e planilhas em que cada pessoa escreveu de um jeito. Transformar esse texto em nome, e-mail, telefone, empresa e cargo é trabalho de interpretação, e é aí que o Claude ajuda.

Para o resultado entrar no seu script de tratamento, ele precisa chegar sempre com os mesmos campos. "Quase sempre" não serve: em mil registros, uma falha de formato a cada cem são dez paradas do script.

## Conteúdo

### 1. O limite de pedir JSON no prompt

No Nível 2, você pedia o formato de saída no próprio prompt: "responda em JSON com os campos nome, email e telefone". Em uma conversa, funciona. Em um laço, aparecem as variações:

- um texto antes do JSON ("Aqui está o resultado:");
- o JSON dentro de um bloco de código, com crases;
- um campo a menos quando o dado não existe;
- um campo a mais que ninguém pediu, como `observacao`;
- uma categoria fora da lista, como `Vendas` em vez de `Comercial`.

Cada variação quebra o `json.loads` ou o código que vem depois. A solução não é um prompt mais insistente. É tirar o formato das mãos do modelo.

### 2. O que é saída estruturada

Com **saída estruturada**, você envia junto com a requisição a descrição do formato, e a API só deixa o modelo gerar texto que obedeça a essa descrição. O formato deixa de ser um pedido e passa a ser uma restrição.

A descrição é escrita em **JSON Schema**, um padrão para dizer que campos um JSON tem, de que tipo é cada um e quais são obrigatórios. Em Python, um JSON Schema é um dicionário.

```python
ESQUEMA_CONTATO = {
    "type": "object",
    "properties": {
        "nome": {"type": "string"},
        "email": {"type": "string"},
        "telefone": {"type": "string"},
    },
    "required": ["nome", "email", "telefone"],
    "additionalProperties": False,
}
```

| Chave | O que diz |
| --- | --- |
| `type` | O tipo do valor: `object` (dicionário), `array` (lista), `string`, `integer`, `number`, `boolean` |
| `properties` | Os campos do objeto e o esquema de cada um |
| `required` | Os campos que precisam estar presentes |
| `additionalProperties: False` | Nenhum campo além dos listados. A API exige essa linha em todo objeto |
| `enum` | A lista fechada de valores aceitos (seção 5) |

O que a saída estruturada da API não aceita (documentação oficial, novembro de 2026): limites numéricos (`minimum`, `maximum`), tamanho de texto (`minLength`, `maxLength`) e esquemas que se referem a si mesmos. Essas conferências continuam sendo do seu código.

Os trechos das seções 2 a 6 continuam um ao outro. Escreva-os em um arquivo `testar_estrutura.py`.

### 3. A chamada

O esquema vai no parâmetro de formato. A função `chamar` do `claude_util.py` recebe o formato pronto.

```python
import json

import claude_util as cu

FORMATO_CONTATO = {"type": "json_schema", "schema": ESQUEMA_CONTATO}

cliente = cu.criar_cliente()
texto = (
    "Segue o contato da Ana Almeida, compradora da Alimentos Alfa. "
    "Tel 11 99990 0001, e-mail ana.almeida@alfa.example"
)
resposta = cu.chamar(
    cliente,
    [{"role": "user", "content": f"Extraia o contato desta mensagem.\n\n<mensagem>\n{texto}\n</mensagem>"}],
    esforco="low",
    max_tokens=4000,
    formato=FORMATO_CONTATO,
)

if resposta.stop_reason == "end_turn":
    contato = json.loads(cu.texto_da_resposta(resposta))
    print(contato["nome"], "|", contato["email"], "|", contato["telefone"])
else:
    print(f"Sem resultado utilizável: {resposta.stop_reason}")
```

Por baixo, a função envia `output_config={"effort": "low", "format": FORMATO_CONTATO}`. A resposta continua sendo um bloco de texto, e o texto é um JSON que obedece ao esquema. O `json.loads` converte em dicionário, como no módulo P.4.

Na primeira chamada com um esquema novo, a resposta demora um pouco mais, porque a API prepara a restrição. Nas seguintes, a preparação já está guardada.

### 4. O que é garantido e o que não é

| | Garantido? |
| --- | --- |
| O texto é um JSON válido | Sim, se o `stop_reason` for `end_turn` |
| Os campos são os do esquema, com os tipos do esquema | Sim, se o `stop_reason` for `end_turn` |
| O valor de cada campo está correto | Não |
| Há resultado quando o pedido é recusado ou cortado | Não |

Duas consequências práticas:

- **Confira o `stop_reason` antes do `json.loads`.** Uma resposta cortada por `max_tokens` pode trazer um JSON pela metade, e uma recusa pode não trazer JSON nenhum.
- **A saída estruturada garante a forma, não o conteúdo.** O modelo pode pôr o telefone fixo no campo que pedia o celular. O formato estará perfeito e o dado, errado. Por isso a segunda metade deste módulo é sobre medir acerto.

A saída estruturada não pode ser combinada com as citações do módulo 3.2. Se você precisa das páginas e de campos fixos, faça em duas chamadas: uma com citações, para obter os fatos e as páginas, e outra que organiza o texto obtido no formato.

### 5. Listas fechadas com `enum`

Para classificação, o `enum` impede categorias inventadas.

```python
AREAS = ["Compras", "Produção", "Marketing", "Comercial", "Diretoria", "Outros"]
FORMATO_AREA = {
    "type": "json_schema",
    "schema": {
        "type": "object",
        "properties": {"area": {"type": "string", "enum": AREAS}},
        "required": ["area"],
        "additionalProperties": False,
    },
}

resposta = cu.chamar(
    cliente,
    [{"role": "user", "content": "Classifique a área deste cargo: Head of Procurement"}],
    esforco="low",
    max_tokens=4000,
    formato=FORMATO_AREA,
)
print(json.loads(cu.texto_da_resposta(resposta))["area"])
```

A resposta só pode ser um dos seis valores. Inclua sempre uma saída para o caso que não cabe em nenhuma categoria, como `Outros`. Sem ela, o modelo é obrigado a escolher uma categoria errada.

### 6. Dado ausente e divisão de trabalho

**Dado ausente.** O esquema obriga todos os campos a existir. Quando o texto não traz o telefone, o que vai no campo? Decida e escreva nas instruções. Neste módulo, a regra é: texto vazio. A instrução completa diz também o que não fazer: "Quando um dado não estiver no texto, use texto vazio. Não deduza nem complete dados ausentes." Sem a segunda frase, o modelo tende a ser prestativo: monta um e-mail provável a partir do nome e da empresa.

**Divisão de trabalho.** O modelo interpreta. O código padroniza e valida.

| Tarefa | Quem faz | Por quê |
| --- | --- | --- |
| Achar o nome, o e-mail e o telefone no texto | Claude | Exige interpretação |
| Decidir qual dos dois telefones é o celular | Claude | Exige interpretação |
| Passar o e-mail para minúsculas, formatar o telefone como `+55...` | Código | É regra fixa, já testada no seu `validacao.py`, e não custa tokens |
| Conferir se o e-mail é válido | Código | É regra fixa |

Por isso as instruções pedem ao modelo que copie os valores como aparecem. A padronização vem depois:

```python
import validacao as v

bruto = {"nome": "ANA", "email": " Ana.Almeida@ALFA.example", "telefone": "11 99990 0001"}

limpo = {
    "nome": v.capitalizar_nome(bruto["nome"]),
    "email": v.padronizar_email(bruto["email"]),
    "telefone": v.padronizar_telefone(bruto["telefone"]) or "",
}
print(limpo)
print(v.email_valido(limpo["email"]))
```

Pedir ao modelo que também formate o telefone funciona na maioria das vezes. Mas é uma segunda tarefa na mesma chamada, sem teste, paga por token, e os erros dela se misturam com os erros de extração na hora de medir.

### 7. Medir o acerto

Uma extração só pode ser usada em produção depois de medida. O método:

1. **Gabarito.** Um conjunto de registros com a resposta correta, feita ou conferida por uma pessoa. Neste módulo, 50 registros.
2. **Comparação campo a campo**, depois de padronizar os dois lados. `ANA` e `Ana` são o mesmo nome; `(11) 99990-0001` e `+5511999900001` são o mesmo telefone. Sem padronizar, a medição conta diferenças de escrita como erros.
3. **Duas taxas.** Acerto por campo (quantos e-mails corretos em 50) e acerto por registro (quantos registros com todos os campos corretos). A segunda é a que importa para a importação.
4. **Leitura dos erros.** Cada erro é lido e classificado: o modelo errou, a instrução era ambígua ou o gabarito está errado. Os três acontecem.
5. **Ajuste e nova medição.** Uma mudança nas instruções por vez, com a medição antes e depois.

Um cuidado com o passo 5: depois de vários ajustes olhando os mesmos 50 registros, as instruções ficam boas para esses 50, e não necessariamente para os próximos. Desconfie de regras que só servem a um caso. O Nível 5 trata da avaliação com conjuntos separados para ajustar e para medir.

Inclua no gabarito os casos difíceis de propósito. O arquivo do exercício tem quatro:

| Registro | Caso | Comportamento correto |
| --- | --- | --- |
| C07 | Dois telefones, fixo e celular | Usar o celular |
| C19 | Uma segunda pessoa é citada | Extrair o contato principal |
| C33 | E-mail escrito por extenso ("ponto", "arroba") | Converter para o formato de e-mail |
| C41 | Mensagem sem nenhum dado de contato | Todos os campos vazios |

O C41 mede a regra mais importante: não inventar.

### 8. Para saber mais: o atalho com Pydantic

O SDK aceita o formato escrito como uma classe da biblioteca Pydantic, em vez de um dicionário de JSON Schema, e devolve o resultado já convertido. Classes não foram tratadas na Ponte, então este trecho é opcional. Leia como referência.

```python
from pydantic import BaseModel


class Contato(BaseModel):
    nome: str
    email: str
    telefone: str


resposta = cliente.messages.parse(
    model=cu.MODELO,
    max_tokens=4000,
    messages=[{"role": "user", "content": f"Extraia o contato desta mensagem.\n\n<mensagem>\n{texto}\n</mensagem>"}],
    output_format=Contato,
)
contato = resposta.parsed_output
if contato is not None:
    print(contato.nome, contato.email)
```

O esquema é gerado a partir da classe, e `parsed_output` traz um objeto com os campos. O restante do nível usa dicionários, que você já conhece.

## Exemplo aplicado

**Situação.** O comercial de uma feira repassa contatos colhidos em conversas, por e-mail e WhatsApp, colados em uma planilha de uma coluna. Você precisa de um arquivo com nome, sobrenome, e-mail, telefone, empresa e cargo para entrar no seu `tratar_base.py`.

**As instruções de sistema.** Cada regra tem um motivo ligado ao que acontece depois.

```python
SISTEMA = """Você extrai dados de contato de mensagens recebidas por uma equipe de CRM. O resultado é
conferido por um programa e importado em um sistema, então cada campo deve trazer só o dado pedido.

Regras:
- Copie os valores como aparecem no texto. A padronização de telefone e de maiúsculas é feita depois, por código.
- nome é o primeiro nome; sobrenome é o restante do nome da pessoa.
- empresa é o nome da empresa sem o tipo societário (Ltda, S.A.).
- Se houver mais de um telefone, use o celular.
- Se o e-mail estiver escrito por extenso ("ponto", "arroba"), converta para o formato de e-mail.
- Se o texto citar mais de uma pessoa, extraia o contato principal, que é o primeiro apresentado.
- Quando um dado não estiver no texto, use texto vazio. Não deduza nem complete dados ausentes."""

print(len(SISTEMA))
```

Note o tom: frases diretas, com o motivo quando ele ajuda, sem maiúsculas de ênfase. É o que o módulo 1.4 ensinou, e vale igual na API.

**Três entradas e o que se espera.**

| Texto | Ponto de atenção | Resultado esperado |
| --- | --- | --- |
| `ANA IBARRA - COSMÉTICOS GAMA S.A. - Engenheira de Embalagens - ANA.IBARRA@GAMA.EXAMPLE - +55 31 99990-0003` | Tudo em maiúsculas, tipo societário | Valores copiados; `S.A.` fora da empresa. As maiúsculas são corrigidas pelo código |
| `Oi, aqui é Leonardo Macedo, da Higiene Épsilon. Trabalho como coordenador de suprimentos. Meu WhatsApp é 51 99990 0005` | Não há e-mail | `email` vazio. Um e-mail montado a partir do nome é erro |
| `Karina Uchoa \| Analista de Trade Marketing \| Laticínios Eta \| fixo (61) 3333-0007 \| celular (61) 99990-0007 \| karina.uchoa@eta.example` | Dois telefones | O celular |

**A medição.** Depois de rodar os 50 registros, o avaliador mostra o acerto por campo e a lista de erros. Um resultado como "telefone: 49 de 50" com o erro no C07 aponta a regra dos dois telefones: ou ela não está nas instruções, ou não está clara.

As soluções completas estão em [`gabarito/extrair_contatos.py`](gabarito/extrair_contatos.py) e [`gabarito/avaliar_extracao.py`](gabarito/avaliar_extracao.py).

## Erros comuns

- Chamar `json.loads` sem conferir o `stop_reason`.
- Concluir que a extração está correta porque o formato está correto.
- Esquecer `additionalProperties: False` em um objeto do esquema. A API recusa a requisição.
- Fazer uma lista fechada sem a opção para o que não se encaixa.
- Não dizer o que fazer com dado ausente, e receber dados deduzidos.
- Pedir ao modelo a padronização que o código já faz.
- Comparar com o gabarito sem padronizar os dois lados.
- Ajustar as instruções várias vezes de uma só vez e não saber qual mudança ajudou.
- Tentar usar saída estruturada e citações na mesma requisição.

<summary>Respostas</summary>

1. Garante a forma: um JSON válido, com os campos e os tipos do esquema, quando a resposta termina normalmente. Não garante que os valores estejam corretos, nem que haja resultado em caso de recusa ou corte.
2. Porque uma resposta cortada por `max_tokens` ou recusada pode trazer um JSON incompleto ou nenhum JSON.
3. Porque a formatação é regra fixa, já testada no `validacao.py`, sem custo de tokens. Deixar com o modelo cria uma segunda fonte de erro, que se mistura com os erros de extração.
4. Para medir se o modelo inventa dados quando o texto não traz nenhum. O resultado correto é tudo vazio.
5. Que o e-mail está sempre certo, mas seis registros têm erro em algum outro campo. A taxa por campo não mostra isso: é preciso olhar a taxa por registro e a lista de erros.
