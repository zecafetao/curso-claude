# 4.5 Agent SDK e Managed Agents

**Carga:** 5 h (1 h 30 de leitura, 3 h 30 de exercício)

## Objetivo

Escolher onde um agente roda e quem cuida de cada parte, publicar o agente de estudo de mercado no Claude Agent SDK e no Managed Agents, fazê-lo entregar o resultado como arquivo e rodar por agendamento.

## Por que importa no seu trabalho

O agente do módulo 4.2 roda no seu computador, enquanto o script está aberto. Para virar uma rotina, como um estudo de mercado atualizado no início de cada mês, faltam três coisas: rodar sem você iniciar, guardar o resultado em um lugar previsível e ter um teto de custo que não dependa de você acompanhar.

Há mais de um jeito de resolver isso, e cada um muda o que fica sob sua responsabilidade: quem executa o laço, onde rodam as ferramentas, para onde vão os dados, quem guarda o histórico e quem dispara a execução. Este módulo publica o mesmo agente em duas plataformas e compara as três versões, com a do módulo 4.2.

## Conteúdo

### 1. Três formas de rodar o mesmo agente

| | Executor de ferramentas (módulo 4.2) | Claude Agent SDK | Managed Agents |
| --- | --- | --- | --- |
| O que é | O laço do SDK da API, no seu script | O motor do Claude Code, usado como biblioteca | Agentes hospedados pela Anthropic |
| Você escreve | Instruções, ferramentas, laço e parada | Instruções, ferramentas próprias e permissões | Configuração do agente e do ambiente |
| Ferramentas de arquivo, terminal e web | Você escreve (a web é ferramenta de servidor) | Prontas | Prontas |
| Onde as ferramentas rodam | No seu computador | No seu computador | Em um contêiner da Anthropic, um por sessão |
| Computador precisa estar ligado | Sim | Sim | Não |

Um **contêiner** é um computador virtual isolado, criado para a tarefa e descartado depois. É o que permite ao Managed Agents rodar comandos e gravar arquivos sem acesso ao seu computador.

As três versões usam as mesmas instruções (o `SISTEMA` do módulo 4.2), com adaptações pequenas na forma de entregar o resultado.

### 2. Claude Agent SDK

O **Claude Agent SDK** é o Claude Code transformado em biblioteca. O laço, a leitura e a gravação de arquivos, o terminal, a busca e a leitura da web, a compactação de contexto e o sistema de permissões vêm prontos. Você escreve as instruções, as ferramentas que só você tem e as regras do que o agente pode fazer.

Instalação:

```bash
pip install claude-agent-sdk
```

O pacote traz o Claude Code embutido. A autenticação é pela chave da API, na mesma variável de ambiente `ANTHROPIC_API_KEY` do módulo 3.1, e o custo é cobrado na sua conta da API. Os termos da Anthropic não permitem que produtos feitos com o Agent SDK usem o login de uma assinatura do claude.ai (referência: documentação de novembro de 2026).

A versão de referência está em [`gabarito/agente_sdk.py`](gabarito/agente_sdk.py). Três partes:

**A ferramenta própria.** O perfil dos expositores vem da base da feira, que só você tem. No Agent SDK, ferramentas próprias são publicadas como um servidor MCP dentro do mesmo processo (módulo 4.3):

```python
@tool("perfil_expositores", "Perfil dos expositores atuais da feira por setor, porte, região e faturamento.", {})
async def perfil_expositores(argumentos):
    """Reaproveita a função do módulo 4.2. A ferramenta roda neste processo, no seu computador."""
    return {"content": [{"type": "text", "text": agente_mercado.perfil_expositores.call({})}]}


SERVIDOR_DE_DADOS = create_sdk_mcp_server(name="dados_feira", version="1.0.0", tools=[perfil_expositores])
```

O terceiro argumento de `@tool` é o esquema de entrada; aqui, vazio, porque a ferramenta não tem parâmetros.

**As opções.**

```python
ClaudeAgentOptions(
    model="claude-opus-5-5",
    system_prompt=INSTRUCOES,
    cwd=str(PASTA_SAIDA),                                   # o agente trabalha só nesta pasta
    tools=["WebSearch", "WebFetch", "Read", "Write"],      # ferramentas embutidas disponíveis
    mcp_servers={"dados": SERVIDOR_DE_DADOS},
    allowed_tools=["WebSearch", "WebFetch", "Read", "Write", "mcp__dados__perfil_expositores"],
    permission_mode="dontAsk",           # o que não está em allowed_tools é negado, sem perguntar
    setting_sources=[],                  # não carrega configurações do seu computador
    max_turns=30,
    max_budget_usd=2.0,                  # para quando o custo da execução passar de 2 dólares
    effort="medium",
)
```

| Opção | O que faz | Equivale a |
| --- | --- | --- |
| `cwd` | Pasta de trabalho do agente | Abrir o Claude Code nessa pasta |
| `tools` | Quais ferramentas embutidas existem para o agente. `Bash` e `Edit` ficaram de fora | Restringir as ferramentas |
| `allowed_tools` | Quais rodam sem pedir aprovação | A lista `allow` do módulo 4.4 |
| `permission_mode="dontAsk"` | Recusa tudo o que pediria aprovação | O modo `dontAsk` do módulo 4.4 |
| `setting_sources=[]` | Ignora `CLAUDE.md`, Skills e configurações do seu computador | Um ambiente limpo e previsível |
| `max_turns`, `max_budget_usd` | Limite de voltas e de dólares | `max_iterations` do módulo 4.2, com teto em dinheiro |

O nome da ferramenta própria nas permissões segue o padrão do módulo 4.3: `mcp__` mais o nome do servidor e o da ferramenta.

**O laço.**

```python
async for mensagem in query(prompt=f"Setor: {setor}. Região: {regiao}.", options=opcoes()):
    if isinstance(mensagem, AssistantMessage):
        for bloco in mensagem.content:
            if isinstance(bloco, ToolUseBlock):
                print(f"  [ferramenta] {bloco.name}")
    elif isinstance(mensagem, ResultMessage):
        custo = mensagem.total_cost_usd
        print(f"Resultado: {mensagem.subtype}")
```

`query` devolve as mensagens à medida que o agente trabalha. A última é um `ResultMessage`, com a situação final (`subtype`, que vale `success` quando terminou bem) e o custo estimado.

**A entrega.** Não há ferramenta de entrega com conferência. As instruções pedem que o agente grave `estudo.md` na pasta de trabalho, com a ferramenta `Write`. A conferência passa para depois da gravação (seção 4).

**Uma execução real.** Este script foi executado uma vez no ambiente em que o curso foi escrito, em novembro de 2026. A execução terminou com `success` e custo informado de US$ 0,36. A busca na web funcionou; a leitura das páginas foi bloqueada pela rede daquele ambiente. O agente registrou as lacunas em vez de usar números não lidos, como pedem as instruções. O arquivo gerado está em [`dados/exemplos/estudo_agent_sdk_execucao_real.md`](dados/exemplos/estudo_agent_sdk_execucao_real.md) e foi o exemplo aplicado do módulo 4.2.

### 3. Managed Agents

O **Managed Agents** hospeda o agente na Anthropic. Você descreve o agente e o ambiente uma vez; cada execução cria uma sessão, com um contêiner próprio, e você acompanha os eventos pela API ou pelo Console. O recurso está em fase beta em novembro de 2026: nomes e parâmetros podem mudar. O SDK envia sozinho o cabeçalho de beta.

Quatro conceitos:

| Conceito | O que é | Quantas vezes você cria |
| --- | --- | --- |
| Ambiente (*environment*) | A configuração do contêiner: rede permitida, pacotes | Uma vez |
| Agente (*agent*) | Modelo, instruções e ferramentas, guardados com versão | Uma vez; cada mudança cria uma versão nova |
| Sessão (*session*) | Uma execução do agente, com os arquivos de entrada e o histórico | A cada estudo |
| Evento (*event*) | Cada coisa que acontece na sessão: mensagens, ferramentas, mudanças de situação | O fluxo da sessão |

**Configurar uma vez.** O [`gabarito/gerenciado_configurar.py`](gabarito/gerenciado_configurar.py) cria o ambiente e o agente e guarda os identificadores em `gerenciado.json`:

```python
SITES_PERMITIDOS = ["www.ibge.gov.br", "sidra.ibge.gov.br", "www.gov.br", "www.abre.org.br"]

ambiente = cliente.beta.environments.create(
    name="estudos-de-mercado",
    config={"type": "cloud", "networking": {
        "type": "limited",
        "allowed_hosts": SITES_PERMITIDOS,
        "allow_package_managers": True,      # para instalar o pandas, se o contêiner não tiver
    }},
)

ferramentas = [{
    "type": "agent_toolset_20260401",
    "default_config": {"enabled": True, "permission_policy": {"type": "auto"}},
    "configs": [
        {"name": "web_search", "enabled": True, "allowed_domains": SITES_PERMITIDOS,
         "user_location": {"type": "approximate", "country": "BR"}},
        {"name": "web_fetch", "enabled": True, "allowed_domains": SITES_PERMITIDOS},
    ],
}]
agente = cliente.beta.agents.create(name="Estudo de mercado", model="claude-opus-5-5",
                                    system=INSTRUCOES, tools=ferramentas)
```

- **Rede limitada.** Com `"type": "limited"`, o contêiner só acessa os endereços listados. No Managed Agents, a lista vale também para a busca e a leitura da web: resultados de outros sites são omitidos, e a leitura de uma página fora da lista devolve erro. A lista de sites é, ao mesmo tempo, uma decisão de segurança e uma decisão de fontes. A documentação recomenda repetir a lista em cada ferramenta da web (`allowed_domains`), como no código.
- **O conjunto de ferramentas** `agent_toolset_20260401` traz as ferramentas prontas: terminal, leitura e gravação de arquivos, busca e leitura da web. `permission_policy` define se cada chamada roda direto (`auto`) ou espera aprovação.
- **As instruções** são as do módulo 4.2, com duas trocas: o perfil dos expositores é calculado com Python a partir do arquivo enviado, e o estudo é gravado em `/mnt/session/outputs/estudo.md`.
- **Versões.** Rodar o script de novo atualiza o agente, o que cria uma versão nova. As sessões já criadas continuam na versão delas.

**Executar.** O [`gabarito/gerenciado_executar.py`](gabarito/gerenciado_executar.py) envia o arquivo de expositores, cria a sessão, acompanha os eventos e baixa o resultado:

```python
with open(ARQ_EXPOSITORES, "rb") as arquivo:
    enviado = cliente.files.upload(file=arquivo)

sessao = cliente.beta.sessions.create(
    agent={"type": "agent", "id": ids["agent_id"], "version": ids["agent_version"]},
    environment_id=ids["environment_id"],
    title=f"Estudo de mercado: {setor}, {regiao}",
    resources=[{"type": "file", "file_id": enviado.id, "mount_path": "/mnt/session/dados/empresas_expositoras.csv"}],
    budget={"type": "limit", "max_list_cost": {"amount": "300", "currency": "USD"}},   # 300 centavos: US$ 3
)
```

- `files.upload` envia o arquivo à Anthropic pela Files API (módulo 3.2). `resources` o coloca dentro do contêiner, no caminho indicado.
- `budget` é o teto de custo da sessão, em centavos de dólar, escrito como texto: `"300"` são US$ 3. Ao atingir o teto, a sessão pausa, sem perder o trabalho; aumentar o teto a retoma.

O pedido não vai como uma mensagem comum, e sim como um **resultado esperado** (*outcome*), com critérios:

```python
cliente.beta.sessions.events.send(session_id=sessao.id, events=[{
    "type": "user.define_outcome",
    "description": f"Estudo de mercado do setor {setor} na {regiao}, em /mnt/session/outputs/estudo.md",
    "rubric": {"type": "text", "content": RUBRICA},
    "max_iterations": 3,
}])
```

Com um resultado esperado, um avaliador separado confere o trabalho contra a rubrica e devolve ao agente o que falta, até a rubrica ser atendida ou acabarem as `max_iterations`. É o padrão avaliador e otimizador do módulo 4.1, oferecido pronto. A rubrica do gabarito repete os critérios da conferência do módulo 4.2: quatro seções, fontes numeradas e citadas, lacunas registradas.

Os eventos chegam por um fluxo aberto com `sessions.events.stream`. Os que o script trata:

| Evento | O que significa | O que o script faz |
| --- | --- | --- |
| `agent.message` | Texto do agente | Mostra |
| `agent.tool_use` com `evaluated_permission` igual a `ask` | Uma ferramenta espera aprovação | Nega: ninguém está acompanhando |
| `session.status_idle` com motivo `requires_action` | A sessão parou à espera de uma resposta | Segue no laço, depois de responder |
| `session.status_idle` com outro motivo | O trabalho terminou | Sai do laço |
| `session.status_terminated` | A sessão foi encerrada | Sai do laço |

No fim, o script lista os arquivos gravados pela sessão em `/mnt/session/outputs/` e baixa cada um para a pasta `saida_gerenciado/`.

**Custos.** Além dos tokens e das buscas, o Managed Agents cobra o tempo de sessão em execução, a US$ 0,08 por hora. O histórico das sessões fica guardado na Anthropic até você apagar. Preços e regras de novembro de 2026, da documentação oficial.

Os três scripts do Managed Agents não foram executados com uma chave real. Os nomes de métodos, parâmetros e eventos foram conferidos contra a versão 2.8 do SDK `anthropic` e a documentação de novembro de 2026, e o caminho completo (configurar, executar, negar uma aprovação, baixar o arquivo, agendar) foi executado contra um servidor simulado.

### 4. O arquivo final

Nas três versões, o resultado é um arquivo, mas o caminho até ele muda:

| Versão | Quem grava | Onde | Conferência |
| --- | --- | --- | --- |
| Módulo 4.2 | O seu código, pela ferramenta de entrega | `saida_estudos/` | Antes de gravar: o arquivo só existe se passar |
| Agent SDK | O agente, com a ferramenta `Write` | `saida_sdk/estudo.md` | Depois, por você |
| Managed Agents | O agente, no contêiner | `/mnt/session/outputs/`, baixado para `saida_gerenciado/` | O avaliador do resultado esperado, e depois você |

Nas duas últimas, a conferência por código continua possível, sobre o arquivo gravado. O `agente_mercado.py` tem uma função para isso, que lê as seções e as fontes do Markdown e aplica as mesmas regras da ferramenta de entrega:

```python
import agente_mercado as am

for problema in am.conferir_arquivo("dados_n4/exemplos/estudo_agent_sdk_execucao_real.md"):
    print(problema)
```

```
A fonte [1] não tem endereço válido: use o endereço da página lida ou interno:perfil_expositores para a base de expositores.
```

O estudo real do Agent SDK citou a base interna sem endereço. A execução foi anterior à regra da fonte interna, e sem a ferramenta de entrega nada impediu a gravação. É a diferença prática entre conferir antes e conferir depois: na primeira, o problema volta ao agente, que corrige; na segunda, ele chega até você.

Três cuidados com o arquivo final, em qualquer versão:

- **Nome previsível.** Um nome fixo por tipo de estudo, ou com a data, para que um processo seguinte saiba onde procurar.
- **Pasta própria.** O agente grava só na pasta de saída: o `cwd` do Agent SDK e o `/mnt/session/outputs/` do Managed Agents fazem isso.
- **Rascunho para revisão.** O arquivo é um rascunho. A conferência por código pega problemas de estrutura; a verificação dos números na fonte continua sendo sua (módulo 4.2).

### 5. Execução agendada

Há quatro formas de agendar o agente, com responsabilidades diferentes:

| Forma | Onde roda | Computador ligado | Quando usar |
| --- | --- | --- | --- |
| Agendamento do Managed Agents | Na Anthropic | Não | Agente já publicado no Managed Agents |
| GitHub Actions | Nos servidores do GitHub | Não | Agente em um repositório, com dados que podem ficar no GitHub |
| Agendador de Tarefas do Windows (ou `cron`, no macOS) | No seu computador | Sim | Dados que não podem sair do computador |
| Tarefas agendadas do app (módulo 2.8) | No app do Claude | Depende do tipo de tarefa | Rotinas sem código |

**Agendamento do Managed Agents.** Um **agendamento** (*deployment*) dispara sessões sozinho, em horários definidos por uma expressão **cron**: cinco campos com minuto, hora, dia do mês, mês e dia da semana. `17 9 1 * *` quer dizer "minuto 17, hora 9, dia 1, qualquer mês, qualquer dia da semana": todo dia 1, às 9h17.

```python
agendamento = cliente.beta.deployments.create(
    name="Estudo de mercado mensal",
    agent=ids["agent_id"],
    environment_id=ids["environment_id"],
    resources=[{"type": "file", "file_id": enviado.id, "mount_path": "/mnt/session/dados/empresas_expositoras.csv"}],
    initial_events=[{
        "type": "user.define_outcome",
        "description": f"Estudo de mercado do setor {setor} na {regiao}, em /mnt/session/outputs/estudo.md",
        "rubric": {"type": "text", "content": ge.RUBRICA},
        "max_iterations": 3,
    }],
    schedule={"type": "cron", "expression": "17 9 1 * *", "timezone": "America/Sao_Paulo"},  # dia 1, 9h17
    budget={"type": "limit", "max_list_cost": {"amount": "300", "currency": "USD"}},
)
print(agendamento.schedule.upcoming_runs_at)
```

- `initial_events` é o que cada sessão recebe ao começar: o mesmo resultado esperado da execução manual.
- `timezone` é o fuso horário. Com `America/Sao_Paulo`, o horário é o de Brasília.
- `budget` é copiado para cada sessão disparada.
- `upcoming_runs_at` lista as próximas execuções, em UTC (o horário de referência mundial, 3 horas à frente de Brasília). Confira: para `17 9 1 * *` em Brasília, a primeira deve ser o dia 1 do próximo mês às 12h17 UTC.
- A execução real pode atrasar alguns minutos em relação ao horário listado: a plataforma distribui a carga com uma variação de até 15% do intervalo, limitada a 9 minutos.

O [`gabarito/gerenciado_agendar.py`](gabarito/gerenciado_agendar.py) tem quatro comandos: `criar`, `testar` (dispara uma execução agora, fora do horário), `pausar` e `execucoes` (lista as execuções e os erros). Teste sempre com `testar` antes de confiar no horário. Os arquivos de cada execução são baixados como na execução manual, a partir da sessão criada.

**GitHub Actions.** O fluxo [`gabarito/agendamento/estudo_mensal.yml`](gabarito/agendamento/estudo_mensal.yml) roda o `agente_mercado.py` do módulo 4.2 em uma máquina do GitHub e guarda a pasta de saída como **artefato**, um arquivo que você baixa pela aba **Actions** do repositório:

```yaml
on:
  schedule:
    - cron: "17 12 1 * *"
  workflow_dispatch:
```

O cron do GitHub não tem fuso horário: usa sempre UTC. Por isso o horário é 12h17. `workflow_dispatch` permite disparar à mão, para testar. O agendamento só roda no branch padrão do repositório, e o GitHub pode atrasar execuções em horários de muita demanda. A chave da API fica nos segredos do repositório, como no módulo 4.4. Considere que a base de expositores precisa estar no repositório para o fluxo usá-la.

**Agendador de Tarefas do Windows.** Para rodar no seu computador, o arquivo [`gabarito/agendamento/estudo_mensal.bat`](gabarito/agendamento/estudo_mensal.bat) entra na pasta dos scripts e chama o Python do ambiente virtual, guardando a saída em `logs/estudo_mensal.log`:

```bat
chcp 65001 > nul
set PYTHONUTF8=1
cd /d "%~dp0"
if not exist logs mkdir logs
echo ==== %date% %time% >> logs\estudo_mensal.log
".venv\Scripts\python.exe" agente_mercado.py "indústria de embalagens" "região Sul" >> logs\estudo_mensal.log 2>&1
```

As duas primeiras linhas fazem o terminal e o Python usarem UTF-8, para os acentos chegarem certos. `%~dp0` é a pasta do próprio arquivo `.bat`. Para agendar, no PowerShell:

```powershell
schtasks /Create /TN "Estudo de mercado mensal" /TR "C:\curso\nivel4\estudo_mensal.bat" /SC MONTHLY /D 1 /ST 09:17
```

Troque o caminho pelo da sua pasta. Para testar sem esperar o dia 1: `schtasks /Run /TN "Estudo de mercado mensal"`. A chave vem da variável gravada com `setx` no módulo 3.1. Se o computador estiver desligado no horário, a execução não acontece. No macOS, o equivalente é uma linha no `crontab`; nesse caso, a chave precisa ser definida na própria linha ou em um arquivo lido por ela, porque o `cron` não lê as variáveis do seu terminal.

O fluxo do GitHub Actions e o agendamento no Windows foram escritos a partir das documentações do GitHub e da Microsoft e não foram executados no ambiente de escrita do curso.

**Em qualquer forma de agendamento:**

- Um teto de custo por execução: `budget` no Managed Agents, `max_iterations` e `max_uses` no script, `max_budget_usd` no Agent SDK.
- Um registro de cada execução: a lista de execuções do agendamento, o log do GitHub Actions ou o arquivo de log local.
- Uma forma de saber que falhou. Uma execução que não roda não avisa ninguém: confira as execuções do mês, ou faça o processo seguinte reclamar quando o arquivo não existir.
- Pausar o que não está em uso. Um agendamento esquecido gasta todo mês.

### 6. O que fica sob a sua responsabilidade

| Responsabilidade | Executor (4.2) | Agent SDK | Managed Agents |
| --- | --- | --- | --- |
| Laço do agente | SDK da API, no seu processo | Claude Code embutido | Anthropic |
| Ferramentas de arquivo, terminal e web | Você escreve as de arquivo; a web vem da API | Prontas | Prontas |
| Isolamento | Você: pasta e nome de arquivo fixos no código | Você: `cwd`, `tools` e permissões | Contêiner por sessão e rede limitada |
| Para onde vão os dados de entrada | Só o resumo devolvido pelas ferramentas | Só o que as ferramentas devolvem e o que o agente lê | O arquivo inteiro vai para a Anthropic |
| Histórico das execuções | Você grava, se quiser | Sessões salvas no seu computador | Guardado na Anthropic até você apagar |
| Conferência do resultado | Na ferramenta de entrega | Depois da gravação | Avaliador do resultado esperado e depois da gravação |
| Agendamento | Seu: Windows, cron ou GitHub Actions | Seu | Agendamentos da plataforma |
| Teto de custo | `max_iterations`, `max_uses` | `max_turns`, `max_budget_usd` | `budget` por sessão e por agendamento |
| Custo | Tokens e buscas | Tokens e buscas | Tokens, buscas e tempo de sessão |

A linha "para onde vão os dados" decide muitos casos. A base de expositores tem dados de empresas, sem dados pessoais, e pode ir para o Managed Agents se o contrato com o cliente permitir. Uma base de contatos não deveria: para ela, as ferramentas ficam no seu computador, e só os agregados saem, como em todo o curso. O Managed Agents também aceita ferramentas personalizadas executadas do seu lado, que respondem a eventos da sessão; esse arranjo fica para quando você precisar dele.

## Exemplo aplicado

**Situação.** A coordenação quer o estudo de mercado da indústria de embalagens no Sul atualizado no começo de cada mês, para orientar a prospecção de expositores da próxima edição.

**A decisão.**

| Critério | Análise |
| --- | --- |
| Dados de entrada | A base de expositores tem empresas, sem pessoas. O contrato do cliente permite processamento por fornecedores de tecnologia |
| Quem precisa do resultado | A coordenação, no dia 1, mesmo que você esteja de férias |
| Volume | Uma execução por mês, de alguns minutos |
| Custo | Algumas dezenas de centavos de dólar por execução, mais o tempo de sessão |

O computador ligado é o critério que pesa: no Windows, o estudo dependeria da sua máquina no dia 1. Entre o Managed Agents e o GitHub Actions, o primeiro dispensa colocar a base no repositório e traz o avaliador do resultado esperado.

**O que fica com você.** Rodar `testar` uma vez antes de confiar no horário; conferir o arquivo com `conferir_arquivo` depois de cada execução; verificar os números citados contra as fontes antes de repassar; pausar o agendamento se a prospecção acabar.

**Quando a resposta seria outra.** Se o estudo usasse uma base de contatos, o agendamento ficaria no seu computador, e o estudo só sairia nos dias em que ele estivesse ligado. Privacidade vem antes de conveniência.

## Exercício

**Publicar o agente do módulo 4.2 nas duas opções, entregar o arquivo e agendar.**

Cada execução gasta créditos da API. Anote o custo de todas. O teto de cada versão já está no código do gabarito: US$ 2 no Agent SDK e US$ 3 no Managed Agents.

Parte A, Agent SDK (1 h):

1. Instale o `claude-agent-sdk` no ambiente virtual.
2. Monte o `agente_sdk.py` a partir do gabarito, com as suas instruções do módulo 4.2.
3. Rode para "indústria de embalagens" na "região Sul". Anote o custo, o número de ferramentas chamadas e o tempo.
4. Confira o `saida_sdk/estudo.md` com `conferir_arquivo`. Se houver problemas, ajuste as instruções e rode de novo.

Parte B, Managed Agents (1 h 30):

5. Rode `gerenciado_configurar.py`. Abra o Console e encontre o agente e o ambiente criados.
6. Rode `gerenciado_executar.py` com o mesmo setor e região. Acompanhe a sessão no Console enquanto ela roda.
7. Confira o arquivo baixado com `conferir_arquivo`. Anote o custo e o uso informados no fim.
8. Mude uma linha das instruções, rode o configurar de novo e confirme no Console que o agente ganhou uma versão nova.

Parte C, agendamento (1 h):

9. Crie o agendamento com `gerenciado_agendar.py criar` e confira a primeira data de `upcoming_runs_at`.
10. Rode `testar`, espere a sessão terminar, liste as execuções com `execucoes` e baixe o arquivo da sessão criada.
11. Configure uma segunda forma de agendamento, à sua escolha: o Agendador de Tarefas do Windows com o `.bat` ou o GitHub Actions com o `.yml`. Dispare uma execução manual (`schtasks /Run` ou o botão **Run workflow**) e guarde o log ou o artefato.
12. Pause o agendamento do Managed Agents com `pausar`, a menos que você queira mantê-lo.

Parte D, comparação:

13. Em `publicacao_4.5.md`, preencha a tabela da seção 6 com o que você observou nas três versões (4.2, Agent SDK e Managed Agents): custo, tempo, o que precisou instalar ou configurar, onde ficou o arquivo, o que a conferência encontrou. Termine com a sua escolha para o estudo mensal, justificada pelos critérios do exemplo aplicado.

### Entregável

`agente_sdk.py`, os estudos gerados nas duas plataformas, o log ou artefato do agendamento local ou do GitHub e o `publicacao_4.5.md`.

### Critério de conclusão

- O Agent SDK e o Managed Agents entregaram um `estudo.md`, e a versão final de cada um passa no `conferir_arquivo` sem problemas.
- O agendamento do Managed Agents mostra a primeira execução no dia 1 do próximo mês, às 12h17 UTC, e a execução de teste aparece na lista de execuções.
- A segunda forma de agendamento rodou uma vez e deixou um log ou artefato.
- Todas as execuções tinham teto de custo, e o custo de cada uma está registrado.
- O agendamento do Managed Agents está pausado, ou o `publicacao_4.5.md` diz por que ficou ativo.
- A escolha final cita pelo menos três linhas da tabela da seção 6.

## Erros comuns

- Escolher a plataforma pela novidade, sem olhar para onde vão os dados de entrada.
- Mandar para o Managed Agents uma base com dados pessoais.
- Rodar o Agent SDK sem `tools` e `allowed_tools`, com terminal e edição liberados sem necessidade.
- Esquecer `setting_sources=[]` e ver o agente carregar o `CLAUDE.md` e as Skills do seu computador.
- Escrever o `budget` em dólares (`"3"`), que significa 3 centavos, ou com casas decimais, que é recusado.
- Rede `unrestricted` no ambiente quando a lista de fontes é conhecida.
- Confiar que o agente gravou o arquivo sem conferi-lo depois.
- Usar o horário de Brasília no cron do GitHub Actions, que é sempre UTC.
- Agendar no próprio computador uma tarefa da qual outras pessoas dependem.
- Criar um agendamento e não acompanhar as execuções.
- Esquecer um agendamento ativo, que gasta todo mês.

## Checagem rápida

1. O que o Agent SDK traz pronto que o executor do módulo 4.2 não traz?
2. Para que servem `allowed_tools` e `permission_mode="dontAsk"` juntos?
3. Quais são os quatro conceitos do Managed Agents, e quantas vezes cada um é criado?
4. O que muda quando o pedido é um resultado esperado (*outcome*), e não uma mensagem comum?
5. Em que unidade se escreve o `budget` de uma sessão, e o que acontece quando ele é atingido?
6. Por que o `conferir_arquivo` encontrou um problema no estudo real do Agent SDK que a ferramenta de entrega teria evitado?
7. O que a expressão cron `17 9 1 * *` significa, e por que no GitHub Actions ela vira `17 12 1 * *`?
8. Que critério mais pesa na escolha entre agendar no seu computador e agendar em uma plataforma?

<summary>Respostas</summary>

1. As ferramentas de arquivo, terminal e web, a compactação de contexto e o sistema de permissões do Claude Code.
2. `allowed_tools` lista o que roda sem aprovação; `dontAsk` recusa todo o resto, em vez de esperar uma aprovação que ninguém vai dar.
3. Ambiente e agente, criados uma vez (o agente ganha versões a cada mudança); sessão, criada a cada execução; eventos, que formam o fluxo de cada sessão.
4. Um avaliador separado confere o trabalho contra a rubrica e devolve ao agente o que falta, até a rubrica ser atendida ou acabarem as iterações.
5. Em centavos de dólar, como texto. Ao atingi-lo, a sessão pausa sem perder o trabalho, e aumentar o teto a retoma.
6. Porque no Agent SDK o agente grava o arquivo direto, e a conferência só acontece depois. Com a ferramenta de entrega, a gravação seria recusada e o agente corrigiria a fonte.
7. Todo dia 1, às 9h17. O GitHub Actions usa sempre UTC, três horas à frente de Brasília.
8. Para onde vão os dados. Dados que não podem sair do computador obrigam a agendar nele, mesmo com a desvantagem de ele precisar estar ligado.
