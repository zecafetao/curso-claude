# 4.7 Multiagentes e computer use

**Carga:** 2 h (45 min de leitura, 1 h 15 de exercício)

## Objetivo

Decidir com medição quando dividir um trabalho entre vários agentes compensa, e avaliar quando faz sentido um agente operar uma interface gráfica no lugar de uma pessoa.

## Por que importa no seu trabalho

Dividir o trabalho entre agentes parece natural: um redige, outro confere, como em uma equipe. Às vezes funciona melhor. Muitas vezes custa três vezes mais e entrega o mesmo resultado, ou pior, porque informação se perde na passagem de um agente para o outro.

O mesmo vale para o **computer use**, o recurso que deixa o Claude ver a tela e usar mouse e teclado. Ele permite automatizar sistemas sem API, como uma plataforma de big data que só tem interface web. Também é o jeito mais lento, caro e arriscado de automatizar qualquer coisa.

Este módulo dá os critérios e, no caso dos multiagentes, um experimento para você medir em vez de supor.

## Conteúdo

### 1. Por que dividir

Um sistema **multiagente** tem um agente principal, o **orquestrador**, que divide a tarefa e delega partes a **subagentes**. Cada subagente tem instruções, ferramentas e contexto próprios, e devolve ao orquestrador só o resultado.

| Ganho | Quando aparece |
| --- | --- |
| Contexto separado | Partes que leem muito material: cada subagente lê o seu, e o orquestrador recebe só a conclusão (módulo 4.6) |
| Paralelismo | Partes independentes, que podem rodar ao mesmo tempo, como pesquisar cinco setores |
| Especialização | Instruções e ferramentas diferentes por parte, como um revisor que só lê |
| Verificação independente | Quem confere não é quem escreveu, e não herda as suposições do autor |

| Custo | Por quê |
| --- | --- |
| Mais chamadas e mais tokens | Cada subagente tem o próprio laço, e o orquestrador também |
| Mais tempo | Subagentes em sequência somam os tempos |
| Perda na passagem | O subagente não vê a conversa do orquestrador; só o que foi passado a ele |
| Mais pontos de falha | Cada agente pode errar, e o erro de um contamina o seguinte |

A pergunta não é se o arranjo multiagente funciona, e sim se o ganho paga o custo, para esta tarefa.

### 2. O experimento: redator e revisor

A tarefa é a dos achados do relatório mensal de e-mail: três achados, cada um com título, fato e próximo passo, a partir dos dados de outubro e setembro. Dois arranjos, em [`gabarito/orquestrador.py`](gabarito/orquestrador.py):

| | Agente único | Orquestrador |
| --- | --- | --- |
| Agentes | Um | Três: orquestrador, redator e revisor |
| Ferramentas de dados | `indicadores_email`, `indicadores_por_publico`, `comparar_meses` | As mesmas, nos dois subagentes |
| Fluxo | Consulta os dados e escreve os achados | O orquestrador pede os achados ao redator, envia ao revisor e, se houver problema, pede a correção |
| Chamadas no caminho mais curto | 2 | 7 |

As "chamadas no caminho mais curto" vêm da estrutura, e não de uma medição: o agente único precisa de uma volta para pedir as ferramentas e outra para escrever. O orquestrador precisa de três voltas próprias (pedir ao redator, pedir ao revisor, responder) e de pelo menos duas voltas de cada subagente. Qualquer problema apontado pelo revisor acrescenta mais.

**Subagente como ferramenta.** O jeito mais simples de montar um orquestrador é transformar cada subagente em uma ferramenta do agente principal. A ferramenta, quando chamada, roda outro laço, com outras instruções:

```python
@beta_tool
def revisar_achados(achados_json: str) -> str:
    """Pede ao subagente revisor que confira cada número dos achados contra as ferramentas de dados.

    Args:
        achados_json: A lista JSON de achados devolvida pelo redator.
    """
    sistema = (
        "Você revisa números. Para cada número dos achados, consulte a ferramenta que o produz e confira "
        "o valor. Responda com uma lista JSON de problemas, cada um com numero, trecho e motivo. "
        "Lista vazia se tudo conferir."
    )
    return rodar(cliente, MODELO_REVISOR, sistema, achados_json, FERRAMENTAS_DE_DADOS, total) or "[]"
```

A função `rodar` é o laço do módulo 4.2, com o executor de ferramentas, e soma o uso de todos os agentes no mesmo `total`. O orquestrador vê `redigir_achados` e `revisar_achados` como ferramentas comuns.

O revisor recebe só os achados, sem a conversa do redator. É o que dá a independência: ele confere cada número na ferramenta, sem saber como o redator chegou a ele. Também é o que causa perda: se o redator teve um bom motivo para um número, o revisor não sabe.

**Modelos diferentes por subagente.** `MODELO_REVISOR` pode ser um modelo mais barato. Conferir um número contra uma ferramenta é uma tarefa simples, e o Haiku 5.5 custa um quadragésimo do Opus 5.5 por token (preços de novembro de 2026, módulo 3.5). Testar o revisor com o Haiku é parte do exercício.

### 3. Como medir

Uma comparação justa tem quatro regras:

1. **A mesma tarefa e as mesmas ferramentas** nos dois arranjos. O único que muda é a arquitetura.
2. **Uma avaliação que não depende de nenhum dos arranjos.** A medida de qualidade é `avaliar`, que usa o `verificar_numeros` do projeto: conta, por código, quantos números dos achados existem nos resultados das ferramentas e quantos não existem. A opinião do revisor não serve de medida: seria o arranjo avaliando a si mesmo.
3. **Várias execuções.** O resultado de um agente varia de uma execução para outra. Uma execução de cada não diz qual é melhor.
4. **Custo e tempo junto com a qualidade.** Um arranjo que acerta um número a mais e custa o triplo pode não compensar.

A função `comparar` aplica as quatro regras:

```bash
python orquestrador.py 2026-10 2026-09 5
```

```
{
  "agente_unico": {
    "execucoes": 5,
    "com_tres_achados": ...,
    "numeros_verificados": ...,
    "numeros_sem_fonte": ...,
    "chamadas_por_execucao": ...,
    "custo_medio_usd": ...,
    "segundos_por_execucao": ...
  },
  "orquestrador": { ... }
}
```

Os valores ficam em branco aqui porque dependem do modelo: são a sua medição. O código foi executado no servidor simulado, que confirma o caminho e a contagem, mas não o comportamento do modelo.

A avaliação por código mede uma dimensão da qualidade: números com fonte. Ela não mede se os achados são relevantes nem se os próximos passos fazem sentido. Leia os achados das execuções e anote a sua avaliação ao lado da medição. O Nível 5 trata de avaliar essas dimensões de forma sistemática.

### 4. O que costuma acontecer, e por quê

Sem antecipar o seu resultado, três observações orientam a leitura:

- **Quando as ferramentas devolvem os números prontos**, como aqui, um agente único bem instruído raramente inventa um número. O espaço para o revisor melhorar é pequeno.
- **Uma verificação por código custa quase nada.** O `verificar_numeros` confere todos os números em milissegundos, sem chamadas ao modelo. No projeto deste nível, ele é uma ferramenta do agente de relatórios, e cumpre o papel do revisor para números.
- **O revisor ganha valor quando há o que interpretar**: quando o pedido estimula uma estimativa, ou quando a conferência exige julgamento, como "este próximo passo decorre do fato?".

Por isso o exercício tem um teste de estresse: um pedido que convida o redator a inventar.

### 5. Onde mais você encontra multiagentes

| Onde | Como |
| --- | --- |
| Claude Code | Subagentes em `.claude/agents/`, chamados pelo agente principal (módulo 4.4) |
| Agent SDK | A opção `agents` define subagentes para a sessão (módulo 4.5) |
| Managed Agents | Configuração de multiagente na plataforma, com vários agentes na mesma sessão |
| Pesquisa aprofundada do app | Vários subagentes pesquisam em paralelo e um consolida (módulo 2.5) |

O padrão de pesquisa em paralelo é o caso em que multiagentes mais claramente compensam: as partes são independentes, cada uma lê muito material, e o tempo total cai porque elas rodam ao mesmo tempo.

### 6. Computer use

**O que é.** No **computer use**, o Claude recebe capturas de tela e responde com ações de mouse e teclado. O seu código executa as ações em um computador e devolve uma nova captura. É o laço de ferramentas do módulo 4.2, em que a ferramenta é um computador inteiro.

```python
tools=[{"type": "computer_toolset_20260801"}]
```

O conjunto de ferramentas tem 17 ações, entre elas `screenshot` (capturar a tela), `left_click`, `double_click`, `type` (digitar), `key` (tecla ou atalho), `scroll`, `zoom` e `wait`. O computador é seu: a Anthropic processa as capturas e devolve as ações, mas não hospeda nem guarda o ambiente. A Anthropic publica uma implementação de referência, o `computer-use-demo`, que roda em um contêiner Docker com uma área de trabalho virtual, um navegador e um editor de planilhas.

**Os riscos.**

| Risco | Por quê | Cuidado recomendado pela documentação |
| --- | --- | --- |
| Ações com efeito real | O agente clica em "enviar", "excluir", "aceitar" | Confirmação humana antes de qualquer ação com consequência |
| Instruções escritas na tela | Um texto em uma página ou imagem pode se passar por instrução (injeção, módulo 2.5) | A API tem classificadores que sinalizam injeção nas capturas, mas não os trate como garantia |
| Acesso a dados e contas | O agente vê tudo o que está na tela | Máquina virtual ou contêiner dedicado, sem acesso a dados sensíveis nem a senhas |
| Acesso à internet | O agente pode navegar para qualquer lugar | Restringir a rede a uma lista de sites |

**O custo.** Cada captura de tela custa entre mil e 1.800 tokens de entrada, e uma tarefa simples pode ter dezenas de capturas. A documentação recomenda resolução de 1280 por 720 como ponto de partida e alerta que o modelo pode errar o elemento clicado ou agir como se uma ação tivesse funcionado sem conferir. Cada ação é uma volta do laço, e por isso o computer use é lento.

**Quando considerar.** Antes do computer use, há quatro alternativas, nesta ordem:

| Ordem | Alternativa | Exemplo no seu trabalho |
| --- | --- | --- |
| 1 | Exportação ou API do sistema | A plataforma de big data exporta o estudo de público em CSV |
| 2 | Servidor MCP ou conector | Um conector do CRM (módulos 2.5 e 4.3) |
| 3 | Automação do navegador | O Claude in Chrome (módulo 2.8), ou a ferramenta de uso de navegador da API, que lê e age sobre a página sem precisar de uma área de trabalho inteira |
| 4 | Computer use | Um sistema antigo, sem exportação, que só roda como programa no computador |

No seu dia a dia, o computer use quase sempre perde para a exportação: uma exportação manual de dois minutos, seguida de um script, é mais rápida, barata e confiável que um agente navegando pela plataforma.

Esta seção foi escrita a partir da documentação oficial de novembro de 2026. O computer use não foi executado no ambiente de escrita do curso. Os nomes das ações e o tipo da ferramenta valem para o Opus 5.5, que só aceita o conjunto `computer_toolset_20260801` na API.

## Exemplo aplicado

**Situação.** O agente de relatórios do projeto deste nível escreve as leituras do mês. Você quer saber se um revisor separado melhoraria a confiabilidade dos números antes de entregar o rascunho.

**Antes de medir, as hipóteses.**

| Hipótese | Como verificar |
| --- | --- |
| O revisor reduz números sem fonte | `numeros_sem_fonte` dos dois arranjos, em 5 execuções cada |
| O orquestrador custa pelo menos três vezes mais | `custo_medio_usd` |
| No pedido normal, os dois arranjos empatam em qualidade | As duas medições acima |
| No pedido que convida a estimar, o revisor faz diferença | O teste de estresse do exercício |

**A decisão depois da medição.** Se, como esperado, os dois empatarem no pedido normal e o revisor só fizer diferença no teste de estresse, a escolha para o projeto é o agente único com a verificação por código como ferramenta: ela pega o mesmo problema que o revisor, sem custo de modelo. Se o revisor pegar problemas que a verificação por código não pega, como um próximo passo que não decorre do fato, ele passa a valer o custo, e a medição mostra quanto.

Registrar as hipóteses antes evita a leitura conveniente depois: com os números à frente, é fácil achar um motivo para o arranjo mais sofisticado.

## Erros comuns

- Escolher o arranjo multiagente porque parece mais robusto, sem medir.
- Comparar com uma execução de cada arranjo.
- Usar a opinião do revisor como medida de qualidade do próprio arranjo.
- Comparar só a qualidade, sem custo e tempo.
- Passar ao subagente menos informação do que ele precisa, e culpar o modelo pelo resultado.
- Usar um revisor do mesmo modelo e com as mesmas instruções do redator, sem independência real.
- Usar computer use onde uma exportação ou uma API resolveria.
- Rodar computer use no seu computador de trabalho, com as suas contas abertas.
- Deixar o computer use executar ações com efeito real sem confirmação humana.
