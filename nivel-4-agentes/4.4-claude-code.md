# 4.4 Claude Code

**Carga:** 5 h (1 h 30 de leitura e experimentação, 3 h 30 de exercício)

## Objetivo

Configurar o repositório dos seus scripts para que o Claude Code trabalhe do seu jeito, dentro de limites que você controla: instruções do projeto, permissões, hooks, Skills, subagentes, plugins e execução em integração contínua.

## Por que importa no seu trabalho

No módulo P.5, você usou o Claude Code como par de programação: pediu testes, leu as alterações, fez commits. A cada sessão, você repetia as mesmas orientações ("rode os testes", "não abra a pasta de dados reais") e aprovava os mesmos comandos.

O Claude Code é o agente mais completo que você vai usar neste curso: lê arquivos, edita, roda comandos, busca na web e usa servidores MCP. Ele segue o mesmo desenho do módulo 4.2, com instruções, ferramentas, laço e limites, e você configura cada uma dessas peças por arquivos dentro do repositório. Configurado uma vez, o comportamento vale para todas as sessões e para quem mais usar o repositório.

## Conteúdo

### 1. As camadas de configuração

Cada camada responde a uma pergunta diferente:

| Camada | Pergunta | Arquivo | Tipo de controle |
| --- | --- | --- | --- |
| `CLAUDE.md` | O que o Claude precisa saber sobre o projeto? | `CLAUDE.md` | Contexto: o modelo costuma seguir |
| Permissões | O que ele pode fazer sem perguntar, o que exige aprovação e o que é proibido? | `.claude/settings.json` | Regra: aplicada pelo Claude Code |
| Hooks | O que deve acontecer sempre, antes ou depois de uma ação? | `.claude/settings.json` e scripts | Garantia: executada pelo seu código |
| Skills | Quais procedimentos se repetem? | `.claude/skills/<nome>/SKILL.md` | Procedimento: carregado quando usado |
| Subagentes | Que tarefas pedem um contexto separado e ferramentas restritas? | `.claude/agents/<nome>.md` | Delegação |
| MCP | Que sistemas externos ele acessa? | `.mcp.json` ou cadastro local | Ferramentas (módulo 4.3) |
| Plugins | Como levar tudo isso para outro projeto ou pessoa? | Pacote instalável | Distribuição |

A distinção entre contexto, regra e garantia é a mesma do módulo 3.4. Uma frase no `CLAUDE.md` dizendo "não leia a pasta de dados reais" é um pedido. Uma regra de permissão é aplicada pelo programa. Um hook é código seu, que roda a cada chamada. Para o que não pode acontecer, use as duas últimas.

Os arquivos de referência deste módulo estão em [`gabarito/claude-code/`](gabarito/claude-code/), montados para o repositório de tratamento de bases da Ponte e do Nível 3.

### 2. CLAUDE.md a fundo

O módulo P.5 apresentou o `CLAUDE.md`. Há mais de um, e eles se somam:

| Arquivo | Vale para | Vai para o Git |
| --- | --- | --- |
| `~/.claude/CLAUDE.md` | Todos os seus projetos | Não: fica na sua pasta de usuário |
| `CLAUDE.md` ou `.claude/CLAUDE.md`, na raiz do projeto | Este projeto, para todos que o usarem | Sim |
| `CLAUDE.local.md`, na raiz do projeto | Este projeto, só para você | Não: coloque no `.gitignore` |

No pessoal, ficam preferências suas, como "responda em português". No do projeto, o que qualquer pessoa precisa saber para trabalhar nele.

O `CLAUDE.md` de referência:

```markdown
# Tratamento de bases para o CRM

Scripts em Python que tratam bases de contatos para importação no CRM e calculam os indicadores dos relatórios de campanha.

## Comandos

- Testes: `python -m pytest -q`
- Tratamento de uma base: `python tratar_base.py <base_bruta.csv> <descadastrados.xlsx> <pasta_de_saida>`
- Indicadores do relatório mensal: `python relatorio_mensal.py <mes_atual.csv> <mes_anterior.csv>`

## Organização

- `validacao.py`: uma função por regra de padronização. Toda regra nova tem teste em `test_validacao.py`.
- `tratar_base.py`: o fluxo completo de tratamento. Não contém regras de padronização, só as chama.
- `dados/`: dados fictícios dos exercícios. Bases de clientes reais nunca ficam nesta pasta.

## Regras

- O layout de importação está em @dados_n3/layout_importacao_crm.md. Uma mudança de regra que contrarie o layout precisa de confirmação.
- Mudanças em `validacao.py` vêm com teste. Rode os testes antes de dizer que terminou.
- Não leia nem copie arquivos de `dados_reais/`. As bases reais são tratadas só pelos scripts, sem passar pela conversa.
- Mensagens de commit em português, no imperativo: "Acrescenta regra de UF", "Corrige telefone de 8 dígitos".
```

O que torna esse arquivo útil:

- **Comandos exatos.** O Claude Code não precisa adivinhar como rodar os testes.
- **Onde cada coisa fica, e por quê.** "Não contém regras, só as chama" evita que uma regra nova vá parar no lugar errado.
- **Importação com `@`.** `@dados_n3/layout_importacao_crm.md` traz o conteúdo do layout para o contexto, sem copiá-lo. Quando o layout mudar, o `CLAUDE.md` continua certo.
- **Regras com motivo.** "As bases reais são tratadas só pelos scripts" explica a regra e ajuda o modelo nos casos que ela não cobre.

O que não colocar: o que o modelo já sabe ("escreva código limpo"), o que muda toda semana e textos longos. A documentação recomenda menos de 200 linhas: tudo o que está no `CLAUDE.md` é lido em todas as sessões e ocupa contexto.

Para regras que valem só para uma parte do projeto, use arquivos em `.claude/rules/`, com o campo `paths:` no cabeçalho indicando os arquivos a que se aplicam. Eles só entram no contexto quando o Claude Code trabalha nesses arquivos.

O Claude Code também mantém uma **memória automática**: anotações que ele mesmo grava sobre o projeto ao longo das sessões. O comando `/memory` mostra e edita as duas coisas, o `CLAUDE.md` e a memória automática. Releia de vez em quando: uma anotação errada se repete em todas as sessões.

### 3. Permissões

O arquivo `.claude/settings.json` do projeto define o que o Claude Code pode fazer. A versão de referência:

```json
{
  "permissions": {
    "defaultMode": "default",
    "allow": [
      "Bash(python -m pytest *)",
      "Bash(python tratar_base.py *)",
      "Bash(python relatorio_mensal.py *)",
      "Bash(python graficos_relatorio.py *)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(git commit *)"
    ],
    "deny": [
      "Read(./dados_reais/**)",
      "Edit(./dados_reais/**)",
      "Read(./.env)",
      "Bash(git push *)"
    ]
  }
}
```

**As três listas.**

| Lista | Efeito | No exemplo |
| --- | --- | --- |
| `allow` | Executa sem perguntar | Testes, os três scripts do projeto, `git status` e `git diff` |
| `ask` | Sempre pergunta, mesmo em modos que não perguntariam | Commit: você confere a mensagem e o que entra |
| `deny` | Proíbe | Ler ou editar dados reais, ler o `.env`, enviar ao GitHub |

Quando uma ação se encaixa em mais de uma lista, vale a mais restritiva: `deny` vence `ask`, que vence `allow`.

**A sintaxe.** Cada regra é o nome de uma ferramenta, com um padrão entre parênteses. `Bash(python -m pytest *)` permite o comando `python -m pytest` com quaisquer argumentos. `Read(./dados_reais/**)` cobre todos os arquivos da pasta e das subpastas. Sem parênteses, a regra vale para a ferramenta inteira: `Read` permite ler qualquer arquivo.

Prefira regras estreitas. `Bash(python *)` permitiria rodar qualquer script Python, inclusive um que o próprio Claude Code acabou de escrever. `Bash(python tratar_base.py *)` permite só o tratamento.

**Os arquivos de configuração.** Há vários, e as listas se somam:

| Arquivo | Vale para | Vai para o Git |
| --- | --- | --- |
| `~/.claude/settings.json` | Todos os seus projetos | Não |
| `.claude/settings.json` | O projeto, para todos | Sim |
| `.claude/settings.local.json` | O projeto, só para você | Não |
| Configuração gerenciada | Todos na organização | Definida pelos administradores, e vence as outras |

As regras `deny` e `ask` do projeto valem assim que você abre a pasta. As regras `allow` do projeto só valem depois que você confirma que confia na pasta, para que um repositório baixado da internet não se dê permissões sozinho.

**Os modos de permissão.** O modo define o que acontece com as ações que nenhuma regra cobre.

| Modo | O que faz |
| --- | --- |
| Manual (`default`) | Pergunta antes de editar arquivos, rodar comandos ou acessar a rede. Leituras não perguntam |
| `acceptEdits` | Edita arquivos da pasta sem perguntar; comandos continuam perguntando |
| `plan` | Lê e explora, escreve um plano e não edita nada até você aprovar o plano |
| `auto` | Um modelo verificador separado avalia cada ação e aprova as rotineiras sem perguntar |
| `dontAsk` | Recusa tudo o que perguntaria; só roda o que está em `allow` |
| `bypassPermissions` | Não pergunta nada. Só para ambientes isolados, como contêineres sem acesso à internet |

Desde a versão 2.1.283, as sessões no terminal começam no modo `auto`. A linha `"defaultMode": "default"` faz as sessões deste projeto começarem no Manual. É a escolha recomendada enquanto você aprende a ler o que o Claude Code propõe, e para qualquer projeto em que um erro afete dados de clientes. Um arquivo de projeto não consegue ligar os modos `auto` e `bypassPermissions`: esses só valem quando você escolhe, na configuração pessoal ou durante a sessão. Na extensão do VS Code, o modo inicial não é lido do arquivo do projeto; confira o modo na própria extensão.

No terminal, Shift+Tab troca de modo durante a sessão. O ciclo passa por Manual, `acceptEdits` e `plan`. O comando `/permissions` mostra as regras em vigor.

Em qualquer modo, inclusive `auto` e `bypassPermissions`, as regras `deny` continuam valendo, e as regras `ask` continuam perguntando. Os limites que importam ficam nessas listas, e não na escolha do modo.

Informações de novembro de 2026, da documentação oficial do Claude Code.

### 4. Hooks

Um **hook** é um comando seu que o Claude Code executa automaticamente em um momento definido da sessão. É a camada de garantia: roda sempre, não depende de o modelo lembrar.

| Evento | Quando acontece | Uso típico |
| --- | --- | --- |
| `PreToolUse` | Antes de uma ferramenta rodar | Bloquear uma ação |
| `PostToolUse` | Depois de uma ferramenta rodar | Rodar testes, formatar código |
| `UserPromptSubmit` | Quando você envia um pedido | Acrescentar contexto, barrar pedidos |
| `Stop` | Quando o Claude Code termina de responder | Conferir se o trabalho está completo |
| `SessionStart`, `SessionEnd` | No início e no fim da sessão | Preparar o ambiente, registrar |
| `PreCompact` | Antes de compactar a conversa (módulo 4.6) | Guardar informações |

Os hooks ficam no mesmo `settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Read|Edit|Write|Bash|Grep|Glob",
        "hooks": [
          {"type": "command", "command": "python \"${CLAUDE_PROJECT_DIR}/.claude/hooks/proteger_dados.py\""}
        ]
      }
    ],
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {"type": "command", "command": "python \"${CLAUDE_PROJECT_DIR}/.claude/hooks/rodar_testes.py\""}
        ]
      }
    ]
  }
}
```

`matcher` diz para quais ferramentas o hook roda; a barra vertical quer dizer "ou". `${CLAUDE_PROJECT_DIR}` é a pasta do projeto, para o comando funcionar de qualquer subpasta.

**Como o hook conversa com o Claude Code.** O Claude Code envia ao hook, pela entrada padrão, um JSON com a ferramenta e os parâmetros da chamada. O hook responde pelo código de saída:

| Código de saída | Efeito |
| --- | --- |
| 0 | Segue normalmente |
| 2 | Bloqueia (em `PreToolUse`) ou avisa (em `PostToolUse`). O texto que o hook escreve na saída de erro é mostrado ao Claude como motivo |
| Outro | Erro do hook, mostrado a você; a ação segue |

**Hook 1: proteger os dados reais.** A regra `deny` de `Read` impede a ferramenta de leitura de abrir a pasta. Mas o Claude Code também roda comandos de terminal, e `cat dados_reais/base.csv` lê o arquivo por outro caminho. O hook cobre os dois:

```python
PROTEGIDOS = ("dados_reais", ".env")

entrada = json.load(sys.stdin)
ferramenta = entrada.get("tool_name", "")
parametros = entrada.get("tool_input", {})

# Junta todos os textos da chamada: caminho do arquivo, padrão de busca, comando do terminal.
alvo = " ".join(str(valor) for valor in parametros.values())

if any(protegido in alvo for protegido in PROTEGIDOS):
    print(f"Bloqueado pelo hook proteger_dados: a ferramenta {ferramenta} tentou acessar {PROTEGIDOS}. "
          "Bases reais são tratadas só pelos scripts. Peça à pessoa que rode o script.", file=sys.stderr)
    sys.exit(2)
sys.exit(0)
```

A mensagem de erro segue a regra do módulo 4.2: diz o que fazer em vez do que foi bloqueado.

O hook é uma segunda camada, não a única. Um comando suficientemente indireto, como um script que monta o nome da pasta aos pedaços, passaria pela verificação de texto. A primeira camada continua sendo a do módulo P.5: bases reais fora da pasta do projeto.

**Hook 2: testes depois de cada edição.** Depois de cada edição em arquivo `.py`, o hook roda o pytest. Se algum teste falhar, sai com código 2, e o fim do relatório do pytest volta ao Claude Code, que corrige antes de continuar:

```python
entrada = json.load(sys.stdin)
arquivo = str(entrada.get("tool_input", {}).get("file_path", ""))
if not arquivo.endswith(".py"):
    sys.exit(0)

resultado = subprocess.run([sys.executable, "-m", "pytest", "-q", "-x"], capture_output=True, text=True,
                           cwd=entrada.get("cwd") or None, timeout=120)
if resultado.returncode not in (0, 5):          # 5: nenhum teste encontrado
    linhas = (resultado.stdout + resultado.stderr).strip().splitlines()
    print("Os testes falharam depois da edição:\n" + "\n".join(linhas[-25:]), file=sys.stderr)
    sys.exit(2)
sys.exit(0)
```

Com esse hook, "rode os testes antes de dizer que terminou" deixa de ser um pedido no `CLAUDE.md` e passa a ser automático.

**Testar um hook sem o Claude Code.** Um hook é um script comum: dá para testá-lo enviando o JSON pela entrada padrão. No PowerShell:

```powershell
'{"tool_name": "Bash", "tool_input": {"command": "cat dados_reais/base.csv"}}' | python .claude/hooks/proteger_dados.py
echo $LASTEXITCODE
```

A resposta esperada é a mensagem de bloqueio e o código 2. Os testes `test_hook_protege_dados_reais` do gabarito fazem isso para três casos.

Cuidados:

- Um hook roda com as suas permissões, sem perguntar. Leia todo hook antes de ativar, principalmente em repositórios de outras pessoas.
- O `python` do comando é o que estiver no caminho do sistema quando o Claude Code foi aberto. Abra o Claude Code com o ambiente virtual ativado, ou o hook de testes não encontrará o pytest.
- Hooks lentos atrasam cada ação. O de testes tem limite de 120 segundos.
- O comando `/hooks` mostra os hooks em vigor.

### 5. Skills e comandos

Uma Skill no Claude Code tem o mesmo formato das Skills do app (módulo 2.5): uma pasta com um `SKILL.md` e, se precisar, arquivos de apoio. No projeto, ela fica em `.claude/skills/<nome>/`. Você a chama digitando `/nome`, e o Claude Code também pode carregá-la sozinho quando a descrição combina com o pedido.

Os antigos **comandos personalizados** (arquivos em `.claude/commands/`) foram unidos às Skills. Os que existem continuam funcionando, e um comando novo é uma Skill.

**Um comando para tratar bases.**

```markdown
---
name: tratar-base
description: Trata uma base bruta de contatos com o tratar_base.py e resume o resultado para importação no CRM.
disable-model-invocation: true
argument-hint: <base_bruta.csv> <descadastrados.xlsx>
allowed-tools: Bash(python tratar_base.py *) Read
---

Trate a base com o script do projeto e resuma o resultado.

1. Rode `python tratar_base.py $0 $1 saida_tratamento`.
2. Leia o `resumo.txt` da pasta de saída. Não abra o `importar.csv` nem o `rejeitados.csv`: eles têm dados pessoais.
3. Responda com:
   - linhas lidas, para importar e rejeitadas, com os motivos;
   - os avisos, por tipo;
   - um alerta se as rejeições passarem de 30% das linhas, porque isso costuma indicar um problema na exportação do cliente.
4. Se o script falhar, mostre a mensagem de erro e diga qual coluna ou arquivo parece ser a causa. Não edite o script nesta tarefa.
```

| Campo | O que faz |
| --- | --- |
| `disable-model-invocation: true` | Só roda quando você digita `/tratar-base`. O Claude Code não decide tratar uma base por conta própria |
| `argument-hint` | Lembrete dos argumentos, mostrado quando você digita o comando |
| `allowed-tools` | Ferramentas liberadas sem pergunta enquanto a Skill roda. Aqui, só o script de tratamento e a leitura |
| `$0`, `$1` | O primeiro e o segundo argumentos. `$ARGUMENTS` traz todos juntos |

Uso: `/tratar-base dados/base_bruta_contatos.csv dados/descadastrados.xlsx`.

O passo 2 é uma escolha de privacidade: o resumo tem só contagens, e os arquivos de saída têm contatos. A Skill lê o que é necessário para responder e nada mais.

**A Skill do relatório mensal.** A Skill que você criou no módulo 2.5 funciona no Claude Code sem mudança: copie a pasta `relatorio-mensal-email` para `.claude/skills/`. No app, ela calculava os indicadores escrevendo código a cada vez. No repositório, os scripts já existem e estão testados. Uma seção a mais orienta a Skill a usá-los:

```markdown
## Neste projeto

Este repositório já tem os scripts que fazem os cálculos e os gráficos. Use-os, em vez de escrever código novo:

- Indicadores: `python relatorio_mensal.py <mes_atual.csv> [<mes_anterior.csv>]`.
- Gráficos no padrão visual: `python graficos_relatorio.py <mes_atual.csv> <mes_anterior.csv> saida_graficos`. Cada imagem sai com um CSV dos valores desenhados.

Se um script falhar, mostre o erro e pare. Não corrija o script dentro desta tarefa: a correção é uma mudança de código, com teste, feita à parte.
```

A versão completa está em [`gabarito/claude-code/.claude/skills/relatorio-mensal-email/`](gabarito/claude-code/.claude/skills/relatorio-mensal-email/). Os dois scripts estão na lista `allow` das permissões. Esta Skill não tem `disable-model-invocation`: um pedido como "faça o relatório de outubro" a carrega sozinho.

| Use uma Skill com `disable-model-invocation: true` | Deixe o Claude Code carregar sozinho |
| --- | --- |
| Ações com efeito: tratar uma base, publicar, enviar | Procedimentos de leitura e análise |
| Quando você quer decidir o momento | Quando o pedido em linguagem natural já indica a Skill |

### 6. Subagentes

Um **subagente** é uma instância separada do Claude, com instruções próprias, ferramentas restritas e uma conversa própria. O Claude Code delega a ele uma tarefa e recebe só o resultado. Dois ganhos:

- **Contexto limpo.** Uma revisão que lê dez arquivos não enche a conversa principal com o conteúdo deles: só a conclusão volta.
- **Ferramentas restritas.** Um revisor que só lê não consegue editar, mesmo que tente.

Os subagentes do projeto ficam em `.claude/agents/`. O de referência revisa mudanças nas regras de validação:

```markdown
---
name: revisor-de-regras
description: Revisa mudanças nas funções de validação contra o layout de importação do CRM. Use depois de alterar validacao.py ou antes de um commit que mude regras de padronização.
tools: Read, Grep, Glob
---

Você revisa regras de padronização de bases de contatos.

Compare cada função alterada de validacao.py com dados_n3/layout_importacao_crm.md e com os testes de test_validacao.py.
Para cada função, responda:
- se a regra está de acordo com o layout;
- quais casos de borda não têm teste (vazio, espaços, maiúsculas, acentos, formatos alternativos);
- se a mudança pode alterar o resultado de bases já tratadas.

Não edite arquivos. Responda com uma lista curta por função, do problema mais grave ao menos grave.
```

`name` e `description` são obrigatórios; a descrição diz ao Claude Code quando delegar. `tools` limita as ferramentas: `Read`, `Grep` e `Glob` só leem e buscam. Sem o campo, o subagente herda todas as ferramentas da sessão. Também é possível escolher outro modelo com `model`, por exemplo um mais barato para buscas simples.

Para usar, peça pelo nome ("use o revisor-de-regras na mudança que acabamos de fazer"), ou deixe o Claude Code delegar quando a descrição combinar. O comando `/agents` lista e cria subagentes.

O módulo 4.7 compara, com medição, quando dividir o trabalho entre agentes compensa.

### 7. Plugins

Um **plugin** empacota Skills, subagentes, hooks e servidores MCP em uma unidade que se instala com um comando. Os plugins ficam em **marketplaces**, catálogos que podem ser públicos, da sua empresa ou um repositório seu no GitHub.

| Ação | Como |
| --- | --- |
| Ver e instalar plugins | `/plugin` dentro do Claude Code |
| Instalar pelo terminal | `claude plugin install nome@marketplace` |
| Acrescentar um marketplace | `claude plugin marketplace add <endereço ou repositório>` |
| Desligar ou remover | `claude plugin disable nome` ou `claude plugin uninstall nome` |

Os cuidados de servidores MCP (módulo 4.3) valem em dobro: um plugin pode trazer hooks, que rodam sem perguntar. Instale só de fontes confiáveis e leia o que o plugin contém. O comando `claude plugin details nome` mostra o inventário de componentes.

Para você, plugins serão úteis no Nível 5, quando a configuração deste módulo for compartilhada com colegas. Neste módulo, a configuração fica no próprio repositório, o que já a compartilha com quem o clonar.

### 8. Fora da conversa: modo não interativo e integração contínua

O Claude Code também roda sem conversa, com a opção `-p`: recebe um pedido, trabalha e termina.

```bash
claude -p "Rode os testes e resuma as falhas, se houver." --max-turns 5 --output-format json
```

| Opção | O que faz |
| --- | --- |
| `-p` | Modo não interativo: um pedido, uma resposta |
| `--max-turns` | Limite de voltas do laço, como o `max_iterations` do módulo 4.2 |
| `--max-budget-usd` | Para quando o custo estimado passar do valor |
| `--output-format json` | Resposta em JSON, para outro programa ler |
| `--allowedTools` | Ferramentas liberadas sem pergunta nesta execução |

No modo não interativo, a sessão começa no modo Manual, e não há ninguém para aprovar. Tudo o que a tarefa precisa tem de estar em `allow`, ou ser liberado com `--allowedTools`; o resto é recusado.

**Integração contínua** (CI, de *continuous integration*) é a execução automática de verificações a cada mudança no repositório. No GitHub, isso é feito pelo **GitHub Actions**, com arquivos de fluxo de trabalho (*workflows*) na pasta `.github/workflows/`. A Anthropic publica uma ação pronta, `anthropics/claude-code-action`, que roda o Claude Code dentro do GitHub.

O fluxo de referência responde quando alguém escreve `@claude` em um comentário de *issue* ou de *pull request*:

```yaml
name: Claude Code
on:
  issue_comment:
    types: [created]
  pull_request_review_comment:
    types: [created]
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write
      actions: read
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          claude_args: "--max-turns 10"
```

Para configurar, rode `/install-github-app` dentro do Claude Code: ele instala o aplicativo do Claude no repositório e cria o segredo com a chave. Você precisa ser administrador do repositório e ter o GitHub CLI (`gh`). A chave fica nos **segredos** do repositório (*secrets*), nunca no arquivo do fluxo.

Uma *issue* é um registro de tarefa ou problema no GitHub; um *pull request* é um pedido para juntar uma mudança ao código principal, com revisão. Com o fluxo ativo, você escreve em uma *issue* "@claude acrescente a regra de UF inválida, com testes" e o Claude Code abre um *pull request* com a mudança, que você revisa antes de aceitar.

Custos: os minutos do GitHub Actions, contados pelo GitHub, e os tokens da API, cobrados na sua conta da Anthropic. Em repositório privado, os minutos gratuitos do GitHub são limitados. A ação também roda em horários agendados, assunto do módulo 4.5.

O fluxo foi escrito a partir da documentação do Claude Code de novembro de 2026 e não foi executado no ambiente de escrita do curso.

### 9. Um fluxo de trabalho completo

Com tudo configurado, entregar uma funcionalidade segue esta sequência:

| Passo | Quem | Camada |
| --- | --- | --- |
| 1. Pedir o plano em modo `plan` | Você pede; o Claude Code explora e propõe | Modo de permissão |
| 2. Corrigir e aprovar o plano | Você | |
| 3. Escrever a função e os testes | Claude Code, seguindo o `CLAUDE.md` | Contexto |
| 4. Rodar os testes a cada edição | Hook `PostToolUse` | Garantia |
| 5. Revisar contra o layout | Subagente `revisor-de-regras` | Delegação |
| 6. Fazer o commit | Claude Code propõe; você aprova | Regra `ask` |
| 7. Enviar ao GitHub | Você, no terminal | Regra `deny` |

O envio fica com você de propósito: o commit pode ser desfeito localmente, o envio é público para a equipe.

## Exemplo aplicado

**Situação.** A equipe quer separar, na segmentação, contatos com e-mail corporativo dos que usam e-mail pessoal (Gmail, Hotmail e semelhantes). Você decide acrescentar a função ao `validacao.py`.

**Uma sessão típica.** O relato ilustra o fluxo da seção 9. O código final é o do gabarito, executado e testado.

1. No modo `plan`, você pede: "Quero uma função `tipo_de_email` no `validacao.py` que devolva 'pessoal', 'corporativo' ou vazio para e-mail inválido. Proponha a lista de domínios pessoais e os casos de teste."
2. O Claude Code lê o `validacao.py`, vê que `padronizar_email` e `email_valido` já existem e propõe reaproveitá-las, com uma lista de 15 domínios e sete casos de teste, incluindo maiúsculas, espaços e e-mail sem arroba.
3. Você acrescenta à lista um domínio que aparece nas bases dos seus clientes e aprova o plano.
4. O Claude Code escreve a função e os testes. A cada edição, o hook roda o pytest. Na primeira, um teste falha: `"  Bruno@Hotmail.com.br "` voltou como corporativo, porque a padronização não tinha sido chamada antes de separar o domínio. O relatório do pytest volta ao Claude Code pelo hook, e ele corrige.
5. Você pede a revisão ao `revisor-de-regras`. Ele aponta que a lista de domínios é uma decisão de negócio e deve ficar comentada como tal, e que não há teste para domínio com subdomínio, como `contato@mail.empresa.com.br`.
6. O teste do subdomínio entra, o comentário também, e o Claude Code propõe o commit "Acrescenta classificação do tipo de e-mail". Você aprova.
7. Você roda `git push`.

A solução de referência está em [`gabarito/tipo_de_email.py`](gabarito/tipo_de_email.py), com os testes em `gabarito/test_nivel4.py`.

**O que cada camada fez.** O `CLAUDE.md` orientou onde a função ia e que precisava de teste. O hook pegou o erro antes de você ver o código. O subagente encontrou um caso sem teste sem gastar o contexto da conversa principal. As regras garantiram que o commit passasse por você e que o envio fosse seu.

## Erros comuns

- Escrever no `CLAUDE.md` uma proibição que deveria ser regra `deny` ou hook.
- `CLAUDE.md` longo, com o que o modelo já sabe ou o que muda toda semana.
- Regras `allow` largas, como `Bash(python *)`, que liberam qualquer script.
- Confiar no modo `auto` para proteger dados de clientes, em vez de regras `deny`.
- Ativar hooks ou plugins de terceiros sem ler o código.
- Abrir o Claude Code sem o ambiente virtual ativado, e o hook de testes não encontrar o pytest.
- Uma Skill de ação, como tratar uma base, sem `disable-model-invocation: true`.
- Uma Skill que lê os arquivos com dados pessoais quando um resumo bastaria.
- Subagente revisor sem o campo `tools`, que herda a permissão de editar.
- Chave da API escrita no arquivo do fluxo do GitHub Actions, em vez dos segredos do repositório.
- Deixar o Claude Code enviar ao GitHub sem a sua revisão.

## Checagem rápida

1. Qual é a diferença entre uma frase no `CLAUDE.md`, uma regra de permissão e um hook?
2. Quando uma ação se encaixa em `allow` e em `deny`, o que vale?
3. Por que as regras `allow` de um projeto só valem depois que você confia na pasta?
4. Em que modo as sessões começam no terminal nas versões recentes, e como fazer um projeto começar no Manual?
5. O que um hook `PreToolUse` precisa fazer para bloquear uma ação, e como o Claude Code fica sabendo do motivo?
6. Por que a regra `deny` de `Read` não basta para proteger a pasta de dados reais?
7. Para que serve `disable-model-invocation: true` em uma Skill?
8. Que duas vantagens um subagente tem sobre fazer a mesma tarefa na conversa principal?
9. No modo não interativo, o que acontece com uma ação que não está em `allow`?

<details>
<summary>Respostas</summary>

1. A frase é contexto, que o modelo costuma seguir. A regra de permissão é aplicada pelo Claude Code. O hook é código seu, executado a cada ação.
2. Vale a mais restritiva: `deny`.
3. Para que um repositório baixado da internet não se dê permissões sozinho ao ser aberto.
4. No modo `auto`, desde a versão 2.1.283. Com `"defaultMode": "default"` no bloco `permissions` do `.claude/settings.json`.
5. Sair com o código 2. O texto escrito na saída de erro é mostrado ao Claude como motivo.
6. Porque o Claude Code também roda comandos de terminal, e um `cat` lê o arquivo sem usar a ferramenta de leitura. O hook verifica todos os parâmetros, inclusive o comando.
7. Para que a Skill só rode quando você a chama com `/nome`. O Claude Code não a carrega sozinho.
8. Contexto limpo, porque só o resultado volta à conversa principal, e ferramentas restritas, porque ele só pode usar as que o arquivo lista.
9. É recusada, porque não há ninguém para aprovar.
